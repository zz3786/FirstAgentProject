# D46 · 元数据过滤设计文档

> 使用 VectorStore 的过滤表达式，按租户、时间、部门等标签精准过滤
>
> 目标：让"相似但无关"的 chunk 进不了候选集，同时避免跨租户 / 跨部门的越权检索。

---

## 一、背景与目标

### 1.1 现状问题

`HybridSearchService.search(query)` 早期版本是**全局检索**——任何查询都会在所有文档的所有 chunk 里找最相似的。带来三类问题：

| 问题 | 表现 | 后果 |
|---|---|---|
| **越权检索** | 用户 A 的私有文档被用户 B 召回 | 数据泄露 |
| **噪声污染** | "2024财务制度"和"2025财务制度"同时召回 | 模型看到矛盾信息后胡编 |
| **精确性差** | 用户问"研发部报销标准"，财务部条款也被召回 | Top-K 被无关内容占据 |

### 1.2 设计目标

> **在向量检索阶段就用结构化条件做预过滤，让不满足条件的 chunk 根本进不了候选集。**

关键点：**过滤发生在检索时，不是检索后**。Qdrant 在 HNSW 图遍历时就能跳过不匹配点，比"召回 Top-K 再丢弃"高效得多。

## 二、核心设计思想

### 2.1 三层职责分离

```
┌─────────────────────────────────────────────────────┐
│  写入侧（Ingest）                                    │
│  ─────────────────                                   │
│  injectMetadata()  →  把业务维度（tenant / dept /   │
│                        year / security / status）    │
│                        写入 Document.metadata        │
│                        ↓                             │
│  Qdrant: payload   +   MySQL: 表列                   │
└─────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────┐
│  传输侧（Filter 模型）                               │
│  ─────────────────                                   │
│  RagFilter record  →  中立的过滤条件表达             │
│                        ↓                             │
│  同时翻译成：                                        │
│    - Filter.Expression（给 Qdrant）                  │
│    - SQL WHERE 参数（给 MySQL）                      │
└─────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────┐
│  检索侧（Search）                                    │
│  ─────────────────                                   │
│  向量检索（Qdrant Payload Index 过滤）               │
│  + 关键词检索（MySQL B-Tree 过滤）                   │
│  → 融合 → TEI 重排                                   │
└─────────────────────────────────────────────────────┘
```

### 2.2 四个关键决策

**决策 1：过滤维度用 `record` 显式声明，不用 `Map`**

- ❌ `Map<String, Object>` —— 丢失类型信息、调用方不知道传什么、IDE 无法补全
- ✅ `RagFilter` record —— 类型安全、契约显式、IDE 可补全

**决策 2：过滤条件作为"可选维度"，null 表示不过滤**

每个维度都是 Optional 语义——调用方只传关心的维度，其余留 null。避免"必须传全部维度"的僵化契约。

**决策 3：两路检索共用同一个 `RagFilter` 对象**

向量路翻译成 `Filter.Expression`，关键词路翻译成 SQL WHERE 参数。**上层语义统一，下层实现分离**——这是"可移植过滤"的核心。

**决策 4（D54 新增）：`tenant_id` 是硬过滤，优先级最高**

租户隔离是安全底线——不管其他维度如何，`tenant_id` 必须命中。它放在 `toExpression()` 的**第一个**条件。

## 三、数据模型设计

### 3.1 过滤条件模型

`RagFilter` 是一个 `record`——字段顺序对应语义层次：

| 维度 | 类型 | 语义 | 过滤方式 |
|------|------|------|---------|
| **`tenantId`** | String | **D54：租户 ID** | **硬过滤（必命中）** |
| `departments` | List\<String\> | 部门 | IN 多值 |
| `yearFrom` | Integer | 年份下界 | >= |
| `yearTo` | Integer | 年份上界 | <= |
| `docTypes` | List\<String\> | 内容类型 | IN 多值 |
| `sources` | List\<String\> | 来源文件 | IN 多值 |
| `securityLevelMax` | Integer | D46：用户密级 | <= |
| `statuses` | List\<String\> | D46：文档状态 | IN 多值 |

**兼容构造**：

- 5 参（D45 之前）—— `departments / yearFrom / yearTo / docTypes / sources`
- 7 参（D46）—— 加 `securityLevelMax / statuses`
- 主构造 8 参（D54）—— 加 `tenantId`

**工厂方法**：

- `empty()` —— 不过滤
- `forUser(tenantId, securityLevel)` —— D54 常用入口

### 3.2 Metadata 字段约定

| 字段 | 类型 | 来源 | 用途 |
|------|------|------|------|
| `doc_id` | String | `saveFile()` 生成 UUID | 去重键、删除定位 |
| `source` | String | 原文件名 | 展示、来源过滤 |
| `file_path` | String | 存储文件名 | 下载链接生成 |
| `chunk_index` | Integer | 生产者填 | 去重键、排序 |
| `total_chunks` | Integer | 生产者填 | 分块完整性校验 |
| **`tenant_id`** | **String** | **D54：从路径提取** | **租户隔离（硬）** |
| **`department`** | **String** | **D46：从路径 / 文件名推断** | **部门过滤** |
| **`year`** | **Integer** | **D46：从文件名推断** | **年份范围过滤** |
| **`content_type`** | **String** | **解析器填 / 兜底 "text"** | **类型过滤** |
| **`security_level`** | **Integer** | **D46：从文件名推断** | **密级过滤（硬）** |
| **`status`** | **String** | **D46：从文件名推断** | **状态过滤** |
| `page_number` | Integer | PDF 解析器 | 页定位 |
| `sheet_name` | String | `TableExtractService` | 表格专属 |
| `row_start` / `row_end` | Integer | `TableExtractService` | 行定位 |

**加粗的 6 个字段是各阶段新增的过滤维度。**

### 3.3 硬过滤 vs 软过滤

| 类型 | 字段 | null 处理 | 理由 |
|------|------|---------|------|
| **硬过滤** | `tenant_id` | **拒绝** | 租户隔离是安全底线 |
| **硬过滤** | `security_level` | **拒绝** | 密级不够就该看不到 |
| **硬过滤** | `status` | **拒绝** | 作废 / 草稿不该召回 |
| **软过滤** | `department` | **放行** | 入库时统一填 `"公开"` |
| **软过滤** | `year` | **放行** | 入库时统一填 `0`（哨兵） |
| **软过滤** | `content_type` | **放行** | 入库时统一填 `"text"` |

**核心区别**：硬过滤 null → 拒绝；软过滤 null → 入库时已经**替换成默认值**——查询端不感知。

## 四、写入侧流程

### 4.1 流程图

```
文件入库
    ↓
saveFile() → docId / originalName / storedName
    ↓
解析 → List<Document>
    ↓
切片（表格路径跳过）
    ↓
★ injectMetadata(chunks, docInfo, tenantId, filePath)
    ├─ 通用标识：doc_id / source / file_path / chunk_index / total_chunks
    ├─ D54 新增：tenant_id（从路径第一段推断）
    ├─ D46 新增：department / year / content_type
    └─ D46 新增：security_level / status
    ↓
addToVectorStoreInBatches(chunks) → Qdrant（每批 ≤ 10 条，payload 带过滤字段）
    ↓
saveToMysql(chunks, docInfo, tenantId) → MySQL（列同步写入）
```

### 4.2 元数据推断规则

**从** `{listenFilesDir}/{tenantId}/{department}/{file}` **目录结构提取**：

| 维度 | 推断方式 | 兜底值 |
|------|---------|-------|
| `tenant_id` | 路径第 1 段 | `"default"` |
| `department` | 路径第 2 段 | `"公开"` |
| `year` | 文件名正则 `20\d{2}` | `0`（哨兵） |
| `content_type` | 解析器产出 / 兜底 | `"text"` |
| `security_level` | 文件名含"机密/绝密/秘密/内部" | `1`（公开） |
| `status` | 文件名含"作废/草稿/归档" | `"active"` |

> **生产建议**：路径推断只是"演示规则"。生产环境应通过**入库接口参数**或**数据库配置表**显式指定。

## 五、检索侧流程

### 5.1 流程图

```
用户问题 + RagFilter
    ↓
HybridSearchService.search(query, filter, profile, topK)
    ├──────────────────────────────────────────┐
    ↓                                          ↓
① 向量检索（带过滤）                        ② 关键词检索（带过滤）
   vectorSearch(query, topK, filter)          keywordSearchService.search(...)
   ├─ filter.toExpression()                   ├─ tenantId → SQL WHERE（硬）
   ├─ SearchRequest.builder()                 ├─ departments → SQL IN
   │    .filterExpression(expr)               ├─ yearFrom / yearTo → SQL >= / <=
   └─ Qdrant: Payload Index 加速              ├─ security_level → SQL <=（硬）
    ↓                                          └─ status → SQL IN（硬）
    └──────────────────────────────────────────┘
                    ↓
            ③ 融合（weighted / RRF）
                    ↓
            ④ TEI 重排
                    ↓
            ⑤ RagAdvisor 注入 Prompt
```

### 5.2 向量路过滤表达式

`RagFilter.toExpression()` 生成的 `Filter.Expression` 是**多个维度的 AND 组合**：

```
AND(
    tenant_id == 'hospital-a',                ← 硬过滤，最前
    department IN ['财务部', '公开'],
    year >= 2024,
    year <= 2025,
    security_level <= 3,
    status IN ['active']
)
```

**顺序约定**：`tenantId` **永远放最前**——保证即使其他维度为空，租户过滤也生效。

### 5.3 关键词路过滤

通过 MyBatis 动态 SQL 实现——**软过滤维度加 `OR xxx IS NULL`**（兼容老数据），**硬过滤维度保持 `IN` / `<=`**：

| 维度 | SQL 条件 |
|------|---------|
| `tenantId` | `AND tenant_id = #{tenantId}` |
| `departments` | `AND (department IN (...) OR department IS NULL)` |
| `yearFrom` | `AND (year >= #{yearFrom} OR year IS NULL)` |
| `securityLevelMax` | `AND security_level IS NOT NULL AND security_level <= #{...}` |
| `statuses` | `AND status IN (...)` |

## 六、设计要点（核心）

### 要点 1：过滤必须发生在检索阶段，而非检索后

| 方案 | 性能 | 精度 |
|---|---|---|
| **检索后过滤**（先召回 Top-K 再丢弃） | 召回浪费计算 | Top-K 被无关内容占据 |
| **检索时过滤**（Qdrant 在 HNSW 遍历时跳过） | 只召回命中点 | Top-K 全是相关的 |

**Qdrant 的 Payload Index 让检索时过滤几乎零成本** —— 但**必须建索引**，否则退化为全量扫描。

### 要点 2：Redis VectorStore 与 Qdrant 行为不同

| | RedisVectorStore | QdrantVectorStore |
|---|---|---|
| 过滤能力 | 必须显式声明 `metadataFields` | 开箱即用 |
| **未声明时行为** | **静默返回空结果（最坑）** | 正常过滤 |
| 字段类型 | 必须指定 TAG / TEXT / NUMERIC | 动态推断 |

**Redis 必须显式声明**——否则过滤字段不存在 → 查询结果永远为空 → 排查半天。

**Qdrant 要建 Payload Index**——否则大数据量下过滤退化为全量扫描——30 秒的查询变 30 毫秒的场景。

### 要点 3：过滤"无结果"时不能降级

```
❌ 错误：过滤无结果 → 退化为不过滤
    if (results.isEmpty()) {
        results = hybridSearchService.search(query);   // 降级
    }

✅ 正确：无结果就返回空，让模型说"无法回答"
    if (results.isEmpty()) {
        return request;   // 不注入任何资料
    }
```

**降级会破坏过滤的语义**——用户按"财务部"过滤，结果返回研发部内容，等于过滤失效。

### 要点 4：过滤条件的传递用 Advisor param，不用方法参数

- ❌ **错误**：Advisor 方法签名固定（`adviseStream(ChatClientRequest, StreamAdvisorChain)`）—— 无法加参数
- ✅ **正确**：用 `request.context().get("rag_filter")` 传递

`ChatClientRequest.context()` 是 Spring AI 提供的**跨 Advisor 传参通道**——和 `MessageChatMemoryAdvisor` 读 `CONVERSATION_ID` 是同一个机制。

### 要点 5：`year` 存 `Integer`，不存 `String`

- ❌ `meta.put("year", "2024")` —— 范围查询 "99" > "100" 的经典问题
- ✅ `meta.put("year", 2024)` —— Qdrant 自动识别为 Integer，支持 `>= / <=`

### 要点 6：两路检索的过滤必须一致

如果向量路过滤了，但关键词路没过滤，融合时会混入被过滤的 chunk。**两路过滤必须用同一个 `RagFilter` 对象** —— 这是设计的核心保障。

### 要点 7：`@Order(50)` 让索引先于入库扫描

```
QdrantIndexInitializer  @Order(50)   →  建索引
RagStartupRunner        @Order(100)  →  扫描入库
```

**先建索引再入库** —— 否则入库时的过滤字段没有索引，性能差。

### 要点 8（D54）：`tenant_id` 是硬过滤中的硬过滤

- `security_level` / `status` 是"用户可选"的硬过滤（用户可以决定要不要过滤密级）
- `tenant_id` 是"**用户不可选**"的硬过滤——从 Session 提取，前端不可传

**代码上**：`tenant_id` **无条件加到 filter 里**，且**不接受 null**——空租户要么拒绝，要么返回空。

## 七、踩坑清单

| 坑 | 现象 | 解法 |
|---|---|---|
| Redis 未声明 metadataFields | 过滤静默返回空 | `RedisVectorStore.builder().metadataFields(TAG("tenant_id"))` |
| Qdrant 未建 Payload Index | 小数据量正常，大数据量断崖变慢 | `QdrantIndexConfig` 启动时建 |
| metadata 未注入过滤字段 | 过滤报错或永远返回空 | `injectMetadata` 补 `tenant_id` / `department` / `year` / `security_level` / `status` |
| year 存成 String | 范围查询结果错乱 | 存 `Integer`，Qdrant 自动识别为数值型 |
| 过滤后无结果时"降级" | 用户看到不相关的结果 | **绝不降级**——无结果就返回空 |
| MySQL 侧过滤缺字段 | 向量路过滤了，关键词路没过滤 | `rag_chunks` 表加列 + Mapper 动态 SQL |
| **`OR department IS NULL` 引发索引失效** | 大数据量下 MySQL 慢 | 入库时填 `"公开"` 而非 null——**查询端不加 OR** |
| `Filter.Expression` 与字符串混用 | 类型不安全 | 统一用 `Filter.Expression` |
| `PayloadSchemaType` 路径写错 | 编译失败 | 在 `io.qdrant.client.grpc.Collections` 包下 |
| `@Order` 影响 `@Scheduled` | 顺序错乱 | `@Order` 只对 `ApplicationRunner` 生效 |
| `inferDepartment` 硬编码文件名规则 | 部门字段不准确 | 生产环境改为**目录结构推断**或入库参数 |
| **`tenant_id` 从路径提取时用相对路径** | Windows / Linux 路径分隔符不一致 | 用 `Path.relativize()` 而非 `indexOf("testVectorData")` |

## 八、验证清单

### 8.1 单元测试维度

| 测试 | 目的 |
|------|------|
| 按部门过滤 | 只召回目标部门文档 |
| 按年份范围过滤 | 只召回指定区间 |
| **按租户过滤** | **只召回本租户（D54）** |
| 过滤后无结果 | 返回空而非全部 |
| 组合过滤 | 部门 + 年份 + 类型同时生效 |
| 过滤条件为空 | 等价于不过滤 |

### 8.2 SQL 手动验证

**先验证 SQL 再改 Java** —— 避免"改半小时发现 SQL 本身写错"。

```sql
SELECT
    id, doc_id, tenant_id, department, year, content_type,
    MATCH(content) AGAINST('+报销 +标准' IN BOOLEAN MODE) AS score
FROM rag_chunks
WHERE MATCH(content) AGAINST('+报销 +标准' IN BOOLEAN MODE)
  AND tenant_id = 'hospital-a'
  AND department IN ('财务部')
  AND year >= 2024
ORDER BY score DESC
LIMIT 10;
```

### 8.3 Qdrant 手动验证

Qdrant Dashboard → `agent-rag` → 任意点看 payload：

**每个点都应该有**：

- `tenant_id` = `"hospital-a"`
- `department` = `"财务部"`（不是 null）
- `year` = `2024` 或 `0`（不是 null）
- `security_level` = 数字
- `status` = `"active"`

**缺失任何字段** → 该点永远不会被过滤命中。

## 九、一句话总结

> **元数据过滤的价值不在"筛掉不相关的"，而在"让过滤成为检索的默认动作"。**
>
> **Spring AI 的 `Filter.Expression` 提供了跨向量库的可移植语法**，但 **Redis 和 Qdrant 的行为差异是最大的坑** —— Redis 必须显式声明 `metadataFields`，Qdrant 则要建 Payload Index。
>
> **把过滤条件做成 `RagFilter` record 而非散落的 `Map`**，让"合法过滤维度"成为代码里的显式契约，而不是口头约定。
>
> **D54 后，`tenant_id` 是所有过滤维度中优先级最高的硬约束** —— 它保证"用户永远只能看到自己租户的数据"，与其他维度正交。
