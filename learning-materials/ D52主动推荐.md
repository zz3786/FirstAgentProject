# D52 · 主动推荐——基于历史提问，Agent 主动推荐相关文档

> 从"被动回答问题"到"主动发现知识"——让 Agent 在回答之外推荐用户可能感兴趣的文档

---

## 一、核心痛点

现状：Agent 是**纯被动**的——用户问什么，检索什么，答什么。用户不问，Agent 完全不动。

三类真实场景失效：

| 场景 | 期望 | 现状 |
|---|---|---|
| **用户问完当前问题** | 顺带推荐"你可能还关心"的延伸文档 | 只答当前问题，无延伸 |
| **用户浏览某主题后** | 推送同主题下"相关但未提及"的文档 | 需要用户主动追问 |
| **用户长期未登录后回来** | 推荐"你上次关注的话题有更新" | 完全无感知 |

**目标**：Agent 基于**用户历史提问**，在回答之外**主动推荐**可能感兴趣的文档——让用户"发现"而非"搜索"。

---

## 二、推荐 vs 检索——两者的本质区别

| 维度 | 检索（RAG） | **推荐（本课）** |
|---|---|---|
| **触发** | 用户提问时 | **回答后异步 / 定期** |
| **输入** | 当前问题 | **历史提问 + 行为** |
| **输出** | 参考资料（喂给 LLM） | **推荐列表（给用户看）** |
| **目标** | 回答当前问题 | **发现新知识** |
| **相似度** | "和当前问题最相关" | **"和用户兴趣相关但未问过"** |
| **范围** | 单次会话 | **跨会话 + 长期行为** |

**关键区分**：检索是"精准匹配"，推荐是"兴趣拓展"——**推荐的文档不该和当前问题完全重叠，否则只是重复检索结果**。

---

## 三、核心设计思想

### 3.1 三个推荐信号源

| 信号 | 来源 | 作用 |
|---|---|---|
| **历史提问**（主信号） | `CONV_MEM` | "用户最近关心什么话题" |
| **重要事实** | `LTM` | "用户提到过的重要上下文" |
| **显式偏好** | `USER_PREF` | "用户主动说过喜欢什么" |

**主信号是 CONV_MEM**——它记录的是"用户真实问过的问题"——最能反映兴趣。LTM 和 USER_PREF 是**增强信号**——用于加权或过滤。

### 3.2 推荐算法——三步走

```
第一步：提取"兴趣向量"
  从 CONV_MEM 取用户最近 N 轮提问（如最近 20 轮）
  → 每轮问题已有向量
  → 求平均 / 取最新几条的质心 → "用户兴趣向量"

第二步：候选召回
  用"兴趣向量"去 Qdrant 检索
  → 拿到 Top-K 相似文档
  → ★ 关键：排除"已经问过的"和"当前会话涉及的"

第三步：过滤 + 排序
  硬权限过滤（security_level / department）
  → 去重（推荐过的不要重复推）
  → 按相似度排序 → 取 Top-3 返回
```

### 3.3 核心约束：推荐"没问过"的

**推荐的语义是"发现新知识"**——不是"重复已看过的"。

**三道去重**：

| 去重类型 | 方法 |
|---|---|
| **排除用户问过的** | 从 CONV_MEM 里取所有 user_message 的 doc_id 集合——候选里命中则剔除 |
| **排除当前会话涉及** | 从当前会话的检索结果里拿 doc_id——候选里命中则剔除 |
| **排除近期推荐过的** | Redis 存"用户最近 7 天推荐过的 doc_id"——候选里命中则剔除 |

**为什么必须做**——推荐用户已经看过的内容 = 无价值 + 用户反感。

## 四、触发时机——异步，不阻塞主流程

### 为什么不能同步

**同步方案**（不采用）：
```
用户提问 → RAG 检索 → LLM 生成 → 同时算推荐 → 一起返回
```

**问题**：
- 推荐是"锦上添花"——不该让用户等
- 推荐计算需要"用户兴趣向量"——多一次向量检索
- 增加主流程 500ms+ 延迟——**得不偿失**

### 异步方案（采用）

```
用户提问 → RAG 检索 → LLM 生成 → 流式返回（用户看到回答）
                                        ↓
                              doOnComplete 触发
                                        ↓
                                   异步计算推荐
                                        ↓
                         存入 Redis: RECOMMEND:{userId}
                                        ↓
                    前端在回答完成后，调 /chat/recommendations 拉取
```

**关键设计**：
- 推荐计算**在主流程之外**——不阻塞用户
- 结果**暂存 Redis**——前端按需拉取
- **可以失败**——失败不影响主回答

### 为什么不放在 Advisor 里

**和 D47 澄清判定同样的理由**：
- Advisor 只能"增强 Prompt"——不能"返回额外数据"
- 推荐是**给用户的独立数据**——不是 Prompt 的一部分
- 必须放在 ChatService 层——能控制返回结构

## 五、存储设计

### 5.1 推荐结果存储

```
RECOMMEND:{userId} (string / list)
  ├─ 值：JSON 数组——[{doc_id, title, snippet, score}, ...]
  └─ TTL：1 小时——过期后重新计算
```

**为什么 1 小时 TTL**：
- 太短——频繁重算浪费
- 太长——用户偏好变了但推荐不变
- 1 小时是"新鲜度 vs 成本"的平衡

### 5.2 推荐历史存储（去重用）

```
RECOMMEND_HISTORY:{userId} (set)
  └─ 值：最近 7 天推荐过的 doc_id 集合
  └─ TTL：7 天
```

**用途**：推荐前过滤——已经推过的不要重复推。

### 5.3 兴趣向量缓存

```
INTEREST_VECTOR:{userId} (string)
  └─ 值：float[] 的 Base64 或 JSON
  └─ TTL：2 小时
```

**用途**：用户兴趣向量计算成本高（要聚合最近 N 轮提问）——缓存避免重复算。

## 六、完整数据流

```
用户提问："采购流程怎么走"
    ↓
主流程（回答用户问题）
    ├─ 缓存查询
    ├─ 前置 RAG 检索
    ├─ 澄清判定
    ├─ LLM 生成
    └─ 流式返回 → 用户看到回答
    ↓
doOnComplete 触发
    ↓
异步推荐任务（不阻塞）
    ├─ ① 取用户兴趣向量（缓存或现算）
    │     └─ 从 CONV_MEM 取最近 20 轮提问 → 求质心
    ├─ ② Qdrant 检索候选（用兴趣向量）
    │     └─ topK = 10（多召回，后面再筛）
    ├─ ③ 硬权限过滤
    │     └─ security_level ≤ 用户密级
    │     └─ department 符合可见范围
    ├─ ④ 三重去重
    │     └─ 排除问过的（CONV_MEM）
    │     └─ 排除当前会话的
    │     └─ 排除近期推荐过的（RECOMMEND_HISTORY）
    ├─ ⑤ 排序取 Top-3
    └─ ⑥ 存 Redis: RECOMMEND:{userId}
    ↓
前端在回答完成后调 /chat/recommendations?userId=xxx
    ↓
展示推荐列表
```

## 七、冷启动——新用户没历史怎么办

| 用户状态 | 推荐策略 |
|---|---|
| **全新用户**（无任何历史） | 返回**热门文档**（按点击率/更新时间）或**空列表** |
| **< 5 轮提问** | 样本不足——降级为"当前问题相关"（类似 RAG 的延伸） |
| **≥ 5 轮提问** | 用兴趣向量正常推荐 |
| **长期未登录**（> 30 天） | 用历史兴趣向量 + 时间衰减——越久远的提问权重越低 |

**关键**：**样本不足时不硬推**——"空推荐"比"乱推荐"好。

---

## 八、防滥用——四个机制

### 机制 1：硬权限永不绕过

**推荐必须过和检索同样的权限过滤**——`security_level` / `department` 一个都不能少。

**为什么**——推荐和检索一样是"数据暴露"——**放宽权限 = 数据泄露**。

### 机制 2：推荐上限

**最多推荐 3-5 条**——太多用户不看，反而觉得烦。

### 机制 3：推荐频率限制

**每次回答后计算一次即可**——不是"每次刷新都算"。

**前端拉取时**——如果 Redis 里的推荐还在有效期内，直接返回——不重算。

### 机制 4：用户可关闭

**提供开关**：`USER_PREF:recommend_enabled = false`。

**尊重用户选择**——不是所有人都喜欢推荐。

## 九、常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| **推荐阻塞主流程** | 用户等回答时间变长 | 异步计算——doOnComplete 里触发 |
| **推荐超权限文档** | 越权——安全事故 | 硬权限过滤——和检索同一套 |
| **推荐用户已看过的** | 用户反感 | 三重去重（问过的 + 当前的 + 近期推过的） |
| **推荐数量太多** | 用户不看 | 限制 Top-3~5 |
| **冷启动乱推** | 新用户看到不相关内容 | 样本 < 5 时返回空或热门 |
| **兴趣向量计算太频繁** | Redis/Qdrant 压力大 | 缓存 2 小时 |
| **推荐结果永不过期** | 用户偏好变了但推荐不变 | TTL 1 小时 |
| **推荐内容一成不变** | 每次都是同样 3 条 | 推荐历史 7 天去重 |
| **推荐和检索结果重叠** | 推荐 = 当前回答的资料 | 排除当前会话的 doc_id |
| **推荐失败影响主流程** | 推荐挂了导致回答失败 | try-catch 兜底——失败不影响主流程 |

## 十、与现有模块的关系

### 与 D49 个性化检索的区别

| | D49 个性化检索 | **D52 主动推荐** |
|---|---|---|
| **触发** | 用户提问时 | **回答后异步** |
| **影响** | 调整检索参数（权重/过滤） | **额外返回推荐列表** |
| **用户可见** | 不可见（幕后调整） | **可见（推荐卡片）** |
| **数据流** | 融入主流程 | **独立于主流程** |

**两者互补**：D49 让"检索更精准"，D52 让"发现更多可能"。

### 与四层记忆的关系

| 层 | 在推荐里的角色 |
|---|---|
| CHAT | 不参与——推荐是跨会话的 |
| **CONV_MEM** | **主信号**——提取兴趣向量 |
| LTM | 增强信号——重要事实可加权 |
| USER_PREF | 过滤条件——尊重用户开关 |

**核心消费者是 CONV_MEM**——它记录"用户真实问过什么"，是推荐的最佳数据源。

### 架构位置

```
ChatService.streamChatWithMemory
    ├─ 主流程（回答）
    └─ doOnComplete
          └─ recommendationService.asyncGenerate(userId, conversationId)
                ├─ 读 CONV_MEM → 兴趣向量
                ├─ Qdrant 检索候选
                ├─ 过滤 + 去重
                └─ 存 Redis: RECOMMEND:{userId}

新接口 /chat/recommendations
    └─ 从 Redis 读推荐 → 返回给前端
```

**新增服务**：`RecommendationService`——推荐计算与存储。

## 十一、推荐落地顺序

### 阶段 1（本课）：基础推荐 + 异步计算

```
✅ 新增 RecommendationService
✅ ChatService.doOnComplete 触发异步推荐
✅ 新增 /chat/recommendations 接口
✅ 三重去重 + 硬权限过滤
✅ 配置开关：app.recommendation.enabled = false（默认关）
```

### 阶段 2：质量优化

```
□ 兴趣向量加权——近期提问权重更高（时间衰减）
□ 推荐反馈——用户点击/忽略 → 影响后续推荐
□ 多样性——推荐结果按文档类型打散，避免全是同类
```

### 阶段 3：主动推送

```
□ 定时任务——"周报"式推送（每周一邮件/通知）
□ 事件触发——"用户关注的主题有新文档"时推送
□ 个性化摘要——AI 生成"推荐理由"
```

## 十二、一句话总结

> **主动推荐 = "基于历史兴趣 → 发现新知识"——从被动回答到主动拓展。**
>
> **核心设计**：
> - **触发时机**：doOnComplete 异步——不阻塞主流程
> - **主信号**：CONV_MEM 历史提问——兴趣向量
> - **三重去重**：问过的 + 当前的 + 近期推过的——避免重复
> - **硬权限**：和检索同一套——安全底线不可破
> - **冷启动**：样本不足返回空——不硬推
> - **上限**：Top-3~5——多了用户不看
> - **失败降级**：推荐挂了不影响主回答
>
> **和 D49 的关系**：D49 让"检索更精准"，D52 让"发现更多可能"——前者幕后调整，后者前台呈现——**互补，不替代**。
>
> **和四层记忆的关系**：核心消费者是 CONV_MEM——它记录"用户真实问过什么"，是推荐的最佳数据源。
