## D43 · 混合检索调优

### 课程目标
调整 BM25（关键词）与向量检索的权重配比，让两路召回互补而非相互干扰。

### 核心要点

**1. 两种融合策略**
- **加权融合（Weighted）**：分数归一化后按 `w_vec × norm_vec + w_kw × norm_kw` 求和
- **RRF 融合**：`Σ 1/(k + rank)`，只看排名不看分数

**2. 为什么需要归一化**
- 向量路返回 `distance`（0-1，越小越好）
- 关键词路返回 `score`（0-20+，越大越好）
- 两者量纲不同、方向相反——直接相加无意义
- **必须 Min-Max 归一化 + 方向统一**

**3. 为什么选择 Weighted 而非 RRF**
- Weighted 可精细控制两路权重（如向量 0.7、关键词 0.3）
- RRF 天生等权，无法按业务调整
- **当两路质量明显不同时——必须能按权重倾斜**

**4. 评估集设计原则**
- query 用自然语言，不用文档原文
- 关键词用"文档里特有"的词，不用高频通用词
- 一条 query 配 2-3 个关键词（任一命中即算 hit）
- 评估集必须有区分度——不能全是送分题

**5. 中文关键词检索的关键坑**
- **中文没有空格**——`split(" ")` 会把整句当一个词
- 必须用 **2-gram 滑动窗口**切分（与 MySQL `ngram_token_size=2` 对齐）
- **不要用 `+` 前缀**（必须包含）——过于严格导致零召回
- 用 OR 语义 + `MATCH AGAINST` 的 score 自然排序

### 设计流程回顾

```
查询 → 向量路（Qdrant）+ 关键词路（MySQL 全文索引）
     ↓
   归一化（方向统一为"越大越好"）
     ↓
   加权融合 / RRF
     ↓
   TEI 重排（精筛）
     ↓
   Top-K 返回
```

**为什么这样分层**：粗召回交给两路检索，精筛交给 TEI——每层只做一件事，避免"一路包办所有职责"。

## D44 · 表格抽取

### 课程目标
处理 Excel / CSV，转成"保留列语义"的结构化文本。

### 核心要点

**1. Tika 的致命缺陷**
- Tika 解析 Excel 会把表格**压平成流水文本**
- 列与列的对齐关系彻底丢失
- Embedding 后"张三属于研发部"这条语义召不回来

**2. 三种表格描述策略**

| 策略 | 适用 | 原因 |
|---|---|---|
| **Markdown 表格** | 小表（≤30 行） | LLM 理解最好，支持跨列推理 |
| **KV 逐行描述** | 大表分块 | embedding 抓"字段名=值"共现强 |
| **统计摘要** | 数值列 | 支持聚合类问题 |

**3. 关键设计：表头必须随块走**
- 大表按行分块时，**每块必须重复表头**
- 否则后续 chunk 变"无字段名的值列表"——语义全丢
- **这是新手最容易漏的点**

**4. 解析层的技术细节**
- 用 `DataFormatter` 而非 `getStringCellValue()`——后者遇到数值列会崩
- 空表头补占位名（"列1"、"列2"）——避免"=值"的无字段 KV
- 列数补齐——防止某些行短于表头导致 KV 错位

### 设计流程回顾

```
文档解析入口（按后缀分派）
     ├── Excel/CSV → TableExtractService（已按行分块）
     ├── PDF      → PagePdfDocumentReader
     └── 其他     → Tika 万能解析
     ↓
统一 metadata 注入
     ↓
向量化 + MySQL
```

**为什么这样分派**：把"表格 vs 文本"的差异收敛到 `DocumentParseService` 内部，主干保持 6 段 StopWatch 对称——**主干不分支**。

## D45 · 图片 OCR

### 课程目标
对文档中的图片进行文字提取（Tesseract）。

### 核心要点

**1. 三类输入都要考虑**
- 独立图片文件（jpg/png/...）
- 扫描件 PDF 的页面（**无文本层，纯图片**）
- 文档内嵌图片（进阶，本课未做）

**2. Tesseract 的非线程安全**
- native 句柄不是线程安全
- **必须每个线程独立实例**——用 `ThreadLocal` 是最轻量的方案
- 共享实例会导致 native crash（不可被 try-catch）

**3. 超时控制是硬需求**
- 坏图 / 超大图会让 Tesseract 卡死
- 用 `Future.get(timeout)` 强制中断
- 不设超时 → 一批文件全部阻塞

**4. OCR 结果必须清洗**
- Tesseract 对低质量图产生大量噪声字符
- 直接入向量库会污染检索
- 清洗策略：去连续空行、合并连续空格、去掉噪声符号
- **minTextLength 过滤**——少于 N 字视为无有效文本

**5. 扫描件 PDF 的逐页判断**
- 先用 PDFBox 提取文本层
- 空文本的页 → 渲染为图片 → OCR
- **不能整份判断**——混合型 PDF（前几页文本、后几页扫描）很常见
- 300 DPI 是精度与速度的平衡点

**6. 语言包依赖链**
- `chi_sim+eng` 配置 → 加载 chi_sim、eng
- Tesseract 5.x 会**关联加载 `chi_sim_vert`**（竖排增强）
- 缺失会报错但 OCR 仍能跑——补上让日志干净

### 设计流程回顾

```
文档解析入口
     ├── 图片文件   → ImageDocumentReader → OcrService
     ├── PDF       → parsePdf（含逐页 OCR 补丁）
     └── 其他      → Tika
     ↓
OcrService.ocr(image, sourceId)
     ├── ThreadLocal 拿独立 Tesseract 实例
     ├── Future 提交任务
     ├── get(timeout) 强制超时
     └── 清洗 + 长度过滤
```

**为什么 OcrService 只做"图→文"**：职责单一——图片文件、PDF 页都能复用它，不感知上下文。

## D46 · 元数据过滤

### 课程目标
用 VectorStore 的过滤表达式，按时间、部门等标签精准过滤。

### 核心要点

**1. 过滤必须在检索时而非检索后**
- 检索后过滤：先召回 Top-K 再丢弃——浪费计算
- 检索时过滤：Qdrant 在 HNSW 遍历时跳过——几乎零成本
- **前提：必须建 Payload Index**

**2. Redis 和 Qdrant 的行为差异（最大的坑）**

| | RedisVectorStore | QdrantVectorStore |
|---|---|---|
| 过滤能力 | **必须显式声明 metadataFields** | 开箱即用 |
| 未声明时 | **静默返回空** | 正常过滤 |
| 字段类型 | 必须指定 TAG/TEXT/NUMERIC | 动态推断 |

**3. 过滤字段的分类**
- **筛选维度**（前端可传）：department / year / docTypes
- **权限维度**（服务端强制）：securityLevelMax
- **默认策略**（服务端设默认）：status
- **判断标准**："这个参数是筛选范围还是决定权限？"——后者永不交给前端

**4. RagFilter 用 record 而非 Map**
- Map 丢失类型信息、调用方不知合法 key
- record 显式声明"合法过滤维度"——契约清晰、IDE 可补全
- **保留旧构造签名**——避免破坏已有调用点

**5. 过滤结果的传递机制**
- Advisor 方法签名固定，无法加参数
- 用 `ChatClientRequest.context()` 传参——和 `CONVERSATION_ID` 同一机制
- `param()` 拒绝 null——null 时不传这个 key

**6. 过滤无结果时绝不降级**
- 过滤"财务部"返回空 → 就返回空
- 降级为"不过滤"会破坏语义——用户看到不该看的内容
- 让模型说"根据现有资料无法回答"

**7. Payload Index 的建法**
- 启动时用 `ApplicationRunner` 建——保证 QdrantClient 已就绪
- 用 `@Order(50)` 让它在 `RagStartupRunner(100)` 之前执行
- 幂等——已存在时抛异常，捕获后忽略

### 设计流程回顾

```
写入侧：
  文件入库 → injectMetadata 补过滤字段
       ├── department（从目录名推断）
       ├── year（文件名 → 修改时间 → 当前年）
       ├── content_type（解析器填 / 兜底 "text"）
       ├── security_level（默认 1）
       └── status（默认 "active"）
           ↓
  Qdrant payload + MySQL 列

检索侧：
  RagFilter → toExpression() → Qdrant filterExpression
           → cacheKeySuffix() → 语义缓存 key
```

**为什么 filter 要纳入 cache key**：同一 query 在"财务部"和"研发部"过滤下答案不同——不加 filter 会命中错误缓存。

## D47 · Agent 主动追问

### 课程目标
检索结果不明确时，Agent 反问用户澄清。

### 核心要点

**1. 三个"模糊"信号**
- 最高分低（`max(rerank_score) < minTopScore`）
- 高分项太少（`count(score >= 阈值) < minQualifiedDocs`）
- 来源太散（进阶，本课未做）

**2. 决策点必须能"短路"**
- **Advisor 不能短路**——必须走完 `nextCall`
- **工具不能短路**——它是"被调用者"，没有控制流权限
- **只有 ChatService（调用层）能短路**

**3. 三层控制流的能力对照**

| 位置 | 能修改请求 | 能短路 | 决策者 |
|---|---|---|---|
| **ChatService** | ✅ | ✅ | 代码（你） |
| **Advisor** | ✅ | ❌ | 代码（你） |
| **工具** | ❌ | ❌ | LLM |

**4. 前置检索——一次检索，两用**
- 提到 ChatService 层做一次
- 用于①澄清判定 ②传给 RagAdvisor 注入
- **避免重复 embedding / Qdrant 往返 / TEI 重排**
- 通过 `advisor param("prefetched_docs", docs)` 传递

**5. 反问文本的识别机制**
- 前缀 `[CLARIFY]` 让前端识别
- 前端剥离前缀 → 特殊渲染（黄色气泡）
- **反问不存缓存**——否则第二次问还是反问

**6. 工具为什么不参与澄清判定**
- LLM 决定"要不要检查"——但"要不要检查"是系统策略
- 工具返回后 LLM 还会生成一次——反问文本会被加工
- LLM 可能忽略工具结果——"我觉得我能答"
- **判断标准：业务语义选择 vs 系统级策略——后者必须代码强制**

**7. 无结果 ≠ 模糊（后续修复）**
- 早期把"无结果"也当作"模糊"——触发反问
- 但"无结果"可能是"问的不是知识库问题"（如"我叫小明"）
- **修复**：无结果直接走正常流程——只有"有结果但不够好"才澄清

### 设计流程回顾

```
用户请求
   ↓
① 语义缓存查询（命中直接返回）
   ↓
② 前置 RAG 检索（一次检索，两用）
   ↓
③ 澄清判定
   ├── 模糊 → 返回 [CLARIFY] 反问文本，不调 LLM
   └── 明确 / 无结果 → 继续
   ↓
④ 调 LLM（Advisor 链）
   ├── MessageChatMemoryAdvisor
   ├── CompactingChatMemoryAdvisor
   ├── PreferenceAdvisor
   ├── RagAdvisor（用 prefetched_docs，不重复检索）
   ├── MemoryRetrievalAdvisor
   └── ToolLoggingAdvisor
   ↓
⑤ 缓存最终答案（反问走不到这里）
```

**为什么决策点必须在 ChatService**：因为"要不要调 LLM"这个决策**只有调用层能做**。

## D48 · 整合主项目

### 课程目标
将 RAG 模块合并到第一阶段项目中。

### 核心要点

**1. 模块依赖关系**

```
agent-tools  →  agent-memory  →  agent-core  →  agent-api
                    ↑                ↑
              agent-cache  →  agent-rag
```

**2. 分层原则**
- **agent-tools**：给 LLM 调用的工具（@Tool 注解）
- **agent-rag / agent-memory / agent-cache**：领域服务
- **agent-core**：装配层 + 编排层
- **agent-api**：Controller + 全局异常

**3. 避免循环依赖**
- agent-cache 不能依赖 RagFilter（在 agent-rag）——改用 String 传参
- agent-rag 依赖 agent-cache——方向单一

**4. 主干不分支的设计**
- `ingestWithTika` 保持 6 段 StopWatch 对称
- 分派逻辑下沉到 `DocumentParseService`
- `injectMetadata` 用 `putIfAbsent` 幂等

**5. 配置外置原则**
- OCR 路径、语言、超时 → `OcrProperties`
- 检索 topK、权重、阈值 → `RagProperties`
- 澄清阈值 → `ClarificationProperties`
- **改参数不改代码**

## D49 · ToolContext 传递 userId

### 课程目标
让工具方法从"系统上下文"安全拿到 userId，而不是让 LLM 填写。

### 核心要点

**1. 让 LLM 填 userId 是安全漏洞**
- LLM 可能填错 / 幻觉出不存在的 userId
- 恶意 prompt 可能诱导 LLM 填别人的 userId
- **userId 是系统信息，不是业务参数**

**2. 两个通道的职责分离**

| 通道 | 谁填 | 谁读 |
|------|------|------|
| 工具方法参数 | **LLM** | 工具方法 |
| **ToolContext** | **调用方（ChatService）** | 工具方法 |

**3. 调用方怎么传**
- `chatClient.prompt().toolContext(Map.of("userId", fullUserId))`
- 和 Advisor 的 `param` 是同一机制——**旁路通道**

**4. SafeToolCallback 必须重写 2 个 call**
- `call(String)` —— 无 ToolContext 的场景
- `call(String, ToolContext)` —— 带 ToolContext 的场景
- **只重写第一个 → Spring AI 想传 ToolContext 时被拦 → 报错**

**5. 统一的执行骨架**
- 超时 + 异常兜底 + 入参出参日志
- 两个 call 重载共享 `executeSafely(Supplier)`

### 设计流程回顾

```
用户："记住我喜欢喝咖啡"
    ↓
ChatService 调 ChatClient
    .toolContext(Map.of("userId", "hospital-a:user-alice"))   ← 旁路传参
    ↓
LLM 返回 tool_call: savePreference(key="drink", value="咖啡")
    ↓ 只填业务参数，不填 userId
    ↓
SafeToolCallback.call(input, toolContext)   ← 重载 2 被调用
    ↓
PreferenceTools.savePreference(key, value, toolContext)
    ↓
String userId = toolContext.getContext().get("userId")   ← 从旁路取
    ↓
UserPreferenceService.save(userId, key, value)
```

**为什么 userId 不放工具参数**：LLM 不应该有"决定用哪个 userId"的能力——那是系统级的安全边界。

## D50 · 对话历史向量化

### 课程目标
把每一轮对话（user + assistant）向量化后存入 Redis Vector，支持跨会话语义召回。

### 核心要点

**1. 与 LTM 的定位区别**

| | LTM（关键词） | CONV_MEM（向量） |
|---|---|---|
| 写入时机 | 模型主动 save | 每轮自动 |
| 存储内容 | 精炼事实 | 原始对话 |
| 检索方式 | 中文 2-gram | 向量语义 |
| 类比 | 备忘录的要点 | 完整录音档案 |

**2. 存储单元 = 一轮对话**
- **不存单条 user**——召回后没有回答上下文
- **不存单条 assistant**——用户检索用自己的话，难命中
- **存整轮**：`Document.text` = user 消息（检索命中率高），`assistant_message` 放 metadata

**3. 写入时机 = Advisor 链尾**
- 放 `ConversationMemoryAdvisor(order=250)`
- 天然拿到完整的 user + assistant
- 不污染 `ChatService` 业务逻辑

**4. 检索时机 = 独立 Advisor（order=210）**
- 排在 `LongTermMemoryAdvisor(200)` 之后
- LTM 关键词路先召回，D50 向量语义路补足

**5. 触发条件：只在成功响应后写**
- 错误 / 中断 / 反问 → 不写
- 反问不写——否则下次问还是召回它

**6. 三重隔离（后续 D54 加固）**
- 租户隔离：`tenant_id == 'hospital-a'`
- 用户隔离：`user_id == 'xxx'`
- 会话排除：`conversation_id != '{当前}'`

**7. Redis VectorStore 的 TAG 转义坑**
- user_id 含 `-` / `:` 会让 RediSearch 报 `Syntax error`
- **必须转义**：`user-alice` → `user_alice`
- 存和查用**同一规则**——否则不匹配

### 设计流程回顾

```
用户请求 → ChatClient.stream()
    ↓
流式响应正常完成（doOnComplete）
    ↓
ConversationMemoryService.saveTurn(fullUserId, conversationId, turnIndex, userMsg, answer)
    ↓
conversationVectorStore.add(Document)
    ↓
Document 进入 conv-mem 向量索引

下次请求：
  ConversationRetrievalAdvisor(210)
     → 用当前 query 向量检索 conv-mem
     → 过滤：tenant + user + 排除当前会话
     → similarity_threshold 过滤低分
     → 注入 SystemMessage
```

**为什么单独一层而非复用 CHAT**：CHAT 是"按会话隔离、全量注入、原文保留"——D50 是"跨会话、向量召回、原文保留"——**范围不同、检索方式不同、职责不同**。

## D51 · 检索画像

### 课程目标
按用户历史行为或显式偏好，个性化调整检索参数。

### 核心要点

**1. 检索画像 ≠ 用户偏好**
- **用户偏好（USER_PREF）**：注入 Prompt——影响回答风格
- **检索画像（RETRIEVAL_PROFILE）**：调整检索参数——影响召回结果

**2. 三个可调维度**
- **偏好部门**：软加分（不是硬过滤）——命中时排序提前
- **偏好文档类型**：同上
- **权重偏移**：调整 `w_vec` / `w_kw`——更依赖语义 or 关键词

**3. 硬约束：偏移有上限**
- 权重偏移 `|weightBiasVec| ≤ 0.15`——防止画像失控
- 加分系数 `≤ 1.20`——最多加 20%
- **为什么**：防止"用户问过财务部，永远只看财务部"的自我强化偏见

**4. 为什么用加分而非硬过滤**
- 硬过滤：不符合偏好的文档直接排除——降低召回率
- 加分：排序上优先——用户仍能看到全部结果
- **画像只是软偏好，不是权限**

**5. 存储 TTL = 90 天**
- 比 USER_PREF（360 天）短——用户偏好检索方式会变
- 到期自动失效——避免"换工作后还推荐旧部门"

**6. 检索入口从 2 参变 3 参**
- `search(query, filter)` → `search(query, filter, profile)`
- **保留旧重载**——传 `RetrievalProfile.empty()`

**7. 为什么 `getOrder` 走 `context` 而非 Advisor**
- 画像不影响 Prompt——不注入 SystemMessage
- 在 ChatService 里 `retrievalProfileService.get(fullUserId)`
- 传给 `HybridSearchService`——**调整融合权重**

### 设计流程回顾

```
ChatService.streamChatWithMemory
    ↓
RetrievalProfile profile = retrievalProfileService.get(fullUserId)
    ↓
fetchPrefetchedDocs(userInput, filter, profile)
    ↓
HybridSearchService.search(query, filter, profile, topK)
    ↓
weightedFuse(vectorResults, keywordResults, topK, profile)
    ├── wVec = profile.applyWeightBias(baseVec)   ← 权重偏移 + clamp
    └── applyProfileBoost(scores, docs, profile)  ← 画像加分
    ↓
最终 Top-K
```

**为什么画像不改 Prompt**：画像改的是"召回什么"，不是"怎么答"——所以走检索参数，不进 SystemMessage。

## D52 · 主动推荐

### 课程目标
正常回答后，自动追加一个"你可能还想看"的文档推荐块。

### 核心要点

**1. 推荐内容来源：当前 query 为主 + 历史提问补足**
- 主检索用当前问题
- 结果不足 topK 时，用最近 N 条历史提问补

**2. 去重：排除已回答引用的 docId**
- 推荐的是"没看到的"，不是"重复展示的"
- `excludeDocIds` 从 `prefetchedDocs` 提取

**3. 安全底线：必须沿用 RagFilter**
- 不能因为"是推荐"就绕过权限
- 用户看不到的文档，推荐里也不能出现

**4. 实现位置：ChatService 末尾 `concatWith(Flux.defer(...))`**
- **`Flux.defer` 必须**——保证推荐逻辑在主流 complete 后执行
- 不加 `defer` → 推荐会在组装时立刻执行——错位

**5. 失败降级：绝不拖垮主流程**
- `try/catch` 吞异常 → 返回 `Flux.empty()`
- TEI 超时 / Qdrant 慢 → **不阻断已经成功的回答**

**6. 前端识别：`[RECOMMEND]` 前缀**
- 前端特殊渲染成卡片
- 与 `[CLARIFY]` 处理方式一致

**7. 复用 HybridSearchService 的 4 参重载**
- `search(query, filter, profile, topK)` —— topK 自定义
- 推荐用 `recallSize=9`（大于 topK=3）——过滤后剩几条

### 设计流程回顾

```
主流程 LLM 回答完成
    ↓
mainStream.concatWith(Flux.defer(() -> buildRecommendationFlux(...)))
    ↓
buildRecommendationFlux
    ├── excludeIds = prefetchedDocs 的 docId 集合
    ├── historyQueries = CHAT 里最近 N 条 user 消息（排除当前）
    ├── recommendationService.recommend(userInput, historyQueries, excludeIds, filter)
    │      ├── 主检索（当前 query，topK=9）
    │      ├── 补足（历史 query）
    │      └── 去重 + 取 top 3
    └── render → [RECOMMEND] 块 → 追加到 SSE 流末尾
```

**为什么 `Flux.defer` 不能省**：`defer` 保证推荐逻辑在订阅时才执行——也就是主流 complete 后——此时 CHAT 里已写入本轮对话，历史提问能取到。

## D53 · 用户兴趣标签

### 课程目标
维护"用户关注的技术领域标签"——带权重的兴趣画像。

### 核心要点

**1. 与 D51 检索画像的边界**

| | D51 检索画像 | D53 兴趣标签 |
|---|---|---|
| 画像对象 | 检索策略（怎么查） | 兴趣领域（关心什么） |
| 字段 | 部门 / 文档类型 / 权重偏移 | Spring AI / RAG / 医疗信息化 |
| 作用点 | 混合检索的权重和加分 | 推荐排序 / Prompt 注入 |

**2. 带权重的标签**
- 每个标签记 `weight` / `lastSeenAt` / `hitCount`
- 命中一次 → `weight += 0.15`（上限 1.0）
- 注入时按权重降序取 TopN

**3. 为什么不是简单的 Set**
- "提过一次 RAG" vs "提过十次 Spring AI"——关注强度不同
- 权重让注入能按重要性排序

**4. TTL = 180 天**
- 兴趣会变——半年不更新自动过期
- 避免"以前喜欢 Java，现在还推 Java"

**5. 容量控制：maxTagsPerUser**
- 超上限时淘汰**权重最低的**
- 防止 Hash 无限膨胀

**6. 触发场景**
- "我在学 Spring AI" → `recordInterest("Spring AI")`
- "我对 RAG 比较感兴趣" → `recordInterest("RAG")`

**7. 注入位置：`UserInterestAdvisor(order=120)`**
- 在 `PreferenceAdvisor(100)` 之后
- 在 `RagAdvisor(150)` 之前

### 设计流程回顾

```
用户："我在学 Spring AI 和 RAG"
    ↓
模型判断"用户明确表达兴趣"
    ↓
tool_call: recordInterest(tag="Spring AI")
tool_call: recordInterest(tag="RAG")
    ↓
InterestTools.recordInterest(tag, toolContext)
    ↓
UserInterestService.record(userId, tag)
    ├── 已存在 → weight += 0.15（上限 1.0）
    └── 不存在 → 初始 weight = 0.3
    ↓
redis.opsForHash().put("USER_INTEREST:" + fullUserId, tag, json)

下次请求：
  UserInterestAdvisor(120)
     → topTags(fullUserId, 5)
     → renderAsSystemText
     → 注入 SystemMessage："用户长期关注的技术领域（按关注度排序）：..."
```

**为什么不合并到 USER_PREF**：USER_PREF 是"结构化单值"（city=合肥），D53 是"带权重的标签集合"——**数据形态、检索方式、注入时机都不同**。

## D54 · 多租户

### 课程目标
让一套系统服务于多个组织（医院 / 公司），数据完全隔离。

### 核心要点

**1. 三层隔离模型**

```
Tenant（租户）
   ↓ 包含
User（用户）
   ↓ 拥有
Session（会话）
```

**2. `fullUserId = tenantId:userId`**
- 拼在一起后所有 Redis key 天然带租户前缀
- `LTM:hospital-a:user-alice`
- **不用改 6 个 Service 的存储逻辑**——零成本隔离

**3. 5 个真实风险**

| # | 风险 | 修复 |
|---|------|------|
| 1 | 前端传任意部门（越权） | ChatController 越权校验 |
| 2 | Redis key 无租户前缀 | fullUserId 拼接 |
| 3 | `findConversationIds` 跨用户泄露 | SCAN + 租户过滤 |
| 4 | RAG 无租户隔离（最严重） | tenant_id 贯穿 Qdrant + MySQL |
| 5 | AuthController 硬编码租户 | 用户 → 租户映射表 |

**4. `RagFilter` 加 `tenantId` 字段**
- 放最前——硬过滤优先级最高
- `toExpression()` 里第一个 `ops.add` —— 无条件加
- **不需要 OR IS NULL**——入库时一定填

**5. `findConversationIds` 用 SCAN 不用 KEYS**

| | KEYS | SCAN |
|---|---|---|
| 复杂度 | O(N)——遍历所有 key | O(1)——游标分批 |
| 阻塞 | **阻塞 Redis 主线程** | 不阻塞 |
| 生产 | ❌ 禁用 | ✅ 推荐 |

**6. 三重保护**：SCAN 分批 + 超时（5s）+ 上限（1000）

**7. Pattern 转义**
- tenantId 含 `*` `?` `[` `]` → 会被当通配符
- **必须转义**——否则跨租户泄露

**8. 审计日志独立 logger**

| 事件 | 类型 |
|------|------|
| LOGIN_OK / LOGIN_FAIL | 认证 |
| CROSS_TENANT | 跨租户尝试 |
| DEPT_DENIED | 越权部门 |
| SENSITIVE | 清空会话 / 缓存 |
| DOC_INGEST / DOC_DELETE | 文档变更 |

**9. `AuditLogger` 的 logger name = "AUDIT"**
- `LoggerFactory.getLogger("AUDIT")` —— 不是 `@Slf4j`
- `<logger name="AUDIT" additivity="false">` 分流到独立文件
- `additivity="false"` 阻止冒泡——避免重复写 app.log

**10. 硬过滤 vs 软过滤**

| 类型 | 字段 | null 处理 |
|------|------|---------|
| **硬** | tenant_id / security_level / status | **拒绝** |
| **软** | department / year / content_type | **入库时替换成默认值** |

**软过滤 null 放行**——靠入库时统一填 `"公开"` / `0` / `"text"` 实现。

### 设计流程回顾

```
AuthController.login
    ↓
从 USER_TENANT 表查 tenantId → 写入 Session
    ↓
ChatController.streamR
    ├── TenantRequestUtils.fullUserId(request) → "hospital-a:user-alice"
    ├── ConversationIdUtils.build(fullUserId, sessionId) → "hospital-a:user-alice:sess-1"
    └── RagFilter(tenantId="hospital-a", ...)
    ↓
ChatService.streamChatWithMemory
    ├── 语义缓存：user_id = "hospital-a:user-alice"
    ├── ConversationIdUtils.extractFullUserId → 各 Advisor 用
    └── toolContext.put("userId", "hospital-a:user-alice")
    ↓
各存储层自动带租户前缀
    ├── Redis: LTM:hospital-a:user-alice
    ├── Qdrant: tenant_id=hospital-a（payload）
    ├── MySQL: tenant_id='hospital-a'
    └── Redis Vector: user_id="hospital-a_user_alice"（转义后）
```

**为什么 `tenant_id` 从路径推断而非入库参数**：当前是"目录扫描"入口——没有 HTTP 请求上下文——路径是唯一能携带租户信息的通道。

## D55 · 异步索引

### 课程目标
用异步任务优化大批量文档导入性能。

### 核心要点

**1. 现状：串行是巨大浪费**
- 每文件耗时 5-20 秒——**大部分在等 embedding API**
- CPU 闲置——理论加速比 = 并发数
- 100 个文件从 30 分钟 → 8 分钟（4 并发）

**2. 生产者-消费者模型**

```
IncrementalUpdateService（扫描器，生产者）
    ↓ 收集待入库文件
AsyncIndexService（调度器）
    ↓ 有界线程池 + 信号量
DocumentIngestService（入库，消费者）
```

**3. 关键设计：有界并发 + 背压**
- 有界线程池（concurrency=4）
- 有界队列（queueCapacity=500）
- `CallerRunsPolicy`——队列满时调用线程自己跑——**不丢任务**

**4. 限流双层**
- `Semaphore`——限制 embedding API 并发
- `minIntervalMs`——文件间最小间隔——防 429

**5. `ingestWithFingerprint` 封装"幂等入库"**
- 查指纹 → 算 hash → 入库 → 写指纹
- **为什么放 DocumentIngestService**
    - `docId` 是 `ingest` 的产物——只有它知道"入库成功了什么"
    - 指纹 = 入库成功的"收据"——收据由经手人打
    - 将来加 HTTP 上传入口——指纹逻辑自动复用

**6. Embedding 分批——阿里云硬限制 ≤ 10 条**
- ❌ `vectorStore.add(chunks)` —— chunks.size() > 10 → HTTP 400
- ✅ `addToVectorStoreInBatches(chunks)` —— 每批 10 条
- **批大小外置**——换供应商时改 yml

**7. 失败隔离 + 进度可观测**
- 每个文件独立 `CompletableFuture`——一个挂不影响其他
- 每 N 个文件打一次进度日志
- `BatchResult(total, success, failed, failedFiles)` 返回汇总

**8. 优雅关闭**
- `waitForTasksToCompleteOnShutdown(true)`
- `awaitTerminationSeconds(60)`
- **应用停止时不丢文件**

**9. 配置分离**
- 原 `RagProperties` 拆成 `IngestProperties` + `RetrievalProperties`
- 新增 `AsyncIndexProperties`
- **摄取 / 检索 / 异步三块独立演进**

**10. 包结构按功能分包（单模块内）**
- `org.example.rag.ingest` / `retrieval` / `shared`
- **为什么不分 Maven 模块**：当前只有 1 个输入源，抽模块是负收益

### 设计流程回顾

```
IncrementalUpdateService.doScanAndUpdate
    ↓
扫描目录 → 对比指纹 → 收集 toIngest（List<Path>）
    ↓
AsyncIndexService.ingestBatch(toIngest)
    ↓
提交 N 个 CompletableFuture 到线程池
┌────────────────────────────────────────┐
│  async-index-1   async-index-2  ...   │  ← 4 并发
│    ├─ Semaphore.acquire()              │  ← 限流
│    ├─ Thread.sleep(200ms)              │  ← 防 429
│    ├─ ingestWithFingerprint(file)      │  ← 幂等入库
│    │    ├── 查指纹（跳过已存在）
│    │    ├── 算 SHA-256
│    │    ├── ingest（解析 + 切片 + 分批向量化 + 存 MySQL）
│    │    └── 写指纹
│    └─ Semaphore.release()              │
└────────────────────────────────────────┘
    ↓
BatchResult(total, success, failed, failedFiles)
```

**效果**：50 个文件从 9 分钟 → 2.5 分钟（3-4 倍提速）。

**为什么不用 `@Async`**：`@Async` 线程池全局共享——和其他异步任务互相影响——独立线程池隔离更稳。

## 跨课程的核心设计哲学

### 1. 主干不分支
所有"文件类型分派"逻辑集中在 `DocumentParseService.parse()`——主干只看 `alreadyChunked` 标志，不知道该文件是表格还是图片。

### 2. 分层——每层只做一件事

```
检索层（粗召回） → 融合层（加权） → 重排层（精筛） → 注入层（Prompt）
```

不让任何一层"包办所有职责"。

### 3. 职责边界清晰
- `DocumentParseService`：文件 → Document
- `TableExtractService`：Excel/CSV → 保留列语义的 Document
- `OcrService`：图片 → 文本
- `injectMetadata`：补通用元数据
- `ingestWithFingerprint`：幂等入库（检查 + 入库 + 记账）
- **每层不越界**

### 4. 契约显式化
- `RagFilter` 用 record 而非 Map
- `ParseResult` 用 record 携带 `alreadyChunked`
- `DocInfo` 用 record 携带 `sourcePath` / `lastModified`
- `BatchResult` 用 record 携带 `total / success / failed / failedFiles`

### 5. 过滤决定权分层
- 筛选维度 → 前端可传
- 权限维度 → 服务端强制（security_level / tenant_id）
- 默认策略 → 服务端设默认（status）

### 6. 缓存 key 语义完整
- `{tenantId}::{filter_suffix}`——包含所有影响输出的因素
- 集合维度排序——顺序无关
- 无过滤时 suffix 为空——结构一致

### 7. 短路权限只属于调用层
- Advisor：能增强，不能短路
- 工具：能拦截执行，不能短路
- **ChatService：唯一能"在 LLM 之前做决策"的位置**

### 8. 数据的完整性 > 功能的完整性
- department / year / tenant_id 一定有值（兜底默认值）
- 无值会导致过滤永远返回空
- **宁可兜底，不可留 null**

### 9. 安全边界不可越
- userId：从 ToolContext 取，不让 LLM 填
- tenantId：从 Session 取，前端不可传
- 越权部门：ChatController 校验——拒绝 ≠ 静默忽略

### 10. 可观测性贯穿
- Advisor 链 `[ENTER]/[EXIT]` 日志
- 审计日志独立 logger
- 异步索引进度日志
- 缓存命中率统计

### 11. 降级优于等待
- TEI 超时 → 用原始顺序（不阻断）
- 推荐失败 → 空 Flux（不阻断主回答）
- 记忆写入失败 → warn（不阻断对话）
- **锦上添花的功能绝不影响主流程**

### 12. 配置外置
- OCR / 检索 / 澄清 / 异步 / 推荐——各有一份 `@ConfigurationProperties`
- **改参数不改代码**

## 一句话总结每课

- **D43**：混合检索的价值不在"用了两路"，而在"让两路互补"——归一化方向统一、中文 2-gram 切分、权重可调。
- **D44**：表格抽取的价值不在"能读 Excel"，而在"保留列语义"——表头随块走、KV 描述、按行切。
- **D45**：OCR 的价值不在"能识别文字"，而在"稳定可控"——ThreadLocal 保线程安全、Future 保超时、清洗保质量。
- **D46**：元数据过滤的价值不在"筛掉不相关的"，而在"让过滤成为检索的默认动作"——Payload Index 加速、cache key 隔离、权限维度不可绕。
- **D47**：主动追问的价值不在"能反问"，而在"知道什么时候该反问"——决策点放在调用层、前置检索一次两用、反问不入缓存。
- **D48**：整合的价值不在"合并代码"，而在"依赖方向单一 + 主干不分支 + 配置外置"。
- **D49**：ToolContext 的价值不在"多一个参数"，而在"系统信息与业务参数分离"——userId 不让 LLM 填、旁路通道传递、安全边界清晰。
- **D50**：对话历史向量化的价值不在"多存一份"，而在"跨会话语义召回"——一轮对话为一个单元、只在成功响应后写、三重隔离。
- **D51**：检索画像的价值不在"个性化"，而在"软偏好影响排序而非硬过滤"——加分系数有上限、权重偏移有 clamp、不阻断召回。
- **D52**：主动推荐的价值不在"推几条链接"，而在"补充用户没想到的"——排除已引用、Flux.defer 延迟执行、失败降级为空。
- **D53**：兴趣标签的价值不在"记住几个词"，而在"带权重的关注度"——权重累加、TTL 衰减、TopN 注入。
- **D54**：多租户的价值不在"加个字段"，而在"tenantId 贯穿全链路"——fullUserId 拼接、硬过滤优先级最高、审计日志独立分流。
- **D55**：异步索引的价值不在"用线程池"，而在"幂等 + 有界并发 + 有界队列"——指纹在入库层、embedding 分批、失败隔离、进度可观测。
