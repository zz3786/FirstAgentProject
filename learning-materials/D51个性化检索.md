# D49 · 个性化检索——根据用户历史偏好调整检索权重

> 从"千人一面"到"千人千面"——让同一问题对不同用户返回不同结果

---

## 一、核心痛点

现状：`hybridSearchService.search(query, ragFilter)` 对所有用户使用**完全相同的参数**（向量权重 0.7、关键词权重 0.3、topK=5、TEI 阈值 0.3）。

三类真实场景失效：

| 场景 | 期望 | 现状 |
|---|---|---|
| **跨部门用户问同一问题** | 财务部张三优先看财务制度，研发部李四优先看研发规定 | 两人拿到相同的"全库 Top-5" |
| **同部门不同关注点** | 小王关注技术规范、小李关注制度流程 | 两人结果相同——两类文档混着 |
| **表达习惯差异** | 术语型用户→关键词权重要高；口语型用户→向量权重要高 | 权重固定，不能按用户倾斜 |

**目标**：从用户历史行为提取"检索偏好"，动态调整过滤、权重、召回参数。

---

## 二、核心设计思想

### 2.1 关键区分：硬权限 vs 软偏好

**这条线划错了就是安全事故。**

| 类型 | 示例 | 能否个性化 |
|---|---|---|
| **硬权限**（安全底线） | `security_level ≤ 用户密级` | ❌ 绝不能因偏好放宽 |
| **软偏好**（体验优化） | "我更关心财务部文档" | ✅ 可以倾斜权重 |

**判断标准**：放宽后会不会导致越权/数据泄露？会 → 硬权限；不会 → 软偏好。

### 2.2 三层映射——从画像到参数

```
第一层：画像构建
  USER_PREF + LTM + CONV_MEM
       ↓ 提取/聚合
  RetrievalProfile（检索画像）
    ├── preferredDepartments
    ├── vectorWeightBias
    ├── topKBias
    └── preferredDocTypes
       ↓
第二层：参数映射
  画像 → RagFilter 扩展 + 融合权重调整 + topK 调整
       ↓
第三层：检索执行
  hybridSearchService.search(query, personalizedParams)
```

**三层各自独立**——画像变了不影响参数映射逻辑，参数映射变了不影响检索执行。

### 2.3 硬约束：倾斜有上限

**个性化必须是"微调"而非"重定向"**：

- 权重倾斜幅度 **≤ 20%**（w_vec 从 0.7 最多调到 0.9）
- 过滤偏好是**加分项**而非硬过滤（"优先召回"不是"只召回"）
- 有**兜底**——个性化后结果太少时回退默认参数

**为什么**——防止"自我强化偏见"：用户第一次问财务部问题，之后**永远只召回财务部**——这不是个性化，是画地为牢。

## 三、可个性化的三个维度

### 维度 1：过滤偏好（软过滤）

**不做硬过滤，做"权重加分"**——融合阶段给符合偏好的文档加权重。

```
用户画像：preferredDepartments = [财务部]

融合时：
  docA（财务部）→ 融合分数 × 1.15   ← 加分
  docB（研发部）→ 融合分数 × 1.00
  docC（市场部）→ 融合分数 × 1.00

效果：财务部排名自然上升，但不排除其他部门
```

**为什么不用硬过滤**——用户问"跨部门流程"时，硬过滤会把相关结果直接排除，反而降低召回率。

### 维度 2：融合权重倾斜（软倾斜）

根据用户表达习惯调整两路权重：

| 用户画像 | 调整 | 理由 |
|---|---|---|
| 历史多用术语（"3.2 条"、"GB/T 12345"） | `w_kw` +0.1 | 术语精确匹配更有效 |
| 历史多用口语（"那个怎么弄"） | `w_vec` +0.1 | 语义理解更有效 |
| 历史查询短（≤ 5 字） | `w_kw` +0.05 | 短查询关键词更可靠 |
| 历史查询长（≥ 20 字） | `w_vec` +0.05 | 长查询语义更丰富 |

**怎么判断"多用术语"**——从 `CONV_MEM` 统计：
- 含数字编号（"3.2"、"第 5 条"）占比 > 30% → 术语偏好
- 平均消息长度 < 8 字 → 短查询偏好

### 维度 3：召回参数调整（软调整）

| 画像特征 | 调整 | 理由 |
|---|---|---|
| 用户经常追问（多轮才满意） | `topK` +2 | 让更多候选进入 LLM |
| 用户很少追问（一轮满意） | `topK` -1 | 减少 Token 浪费 |
| 对相关性要求高（常点"不满意"） | `similarity-threshold` +0.1 | 提高准入 |
| 对覆盖率要求高（常问"还有吗"） | `similarity-threshold` -0.1 | 放宽准入 |

**最保守的调整**——topK 和阈值直接影响体验，必须谨慎。

**建议**：**第一版只做"权重倾斜"（维度 2）**——收益明确、风险最低。

## 四、画像的数据来源

### 来源 1：显式偏好（USER_PREF）——精确但稀疏

```
USER_PREF:user-alice
  ├── city: 合肥
  ├── job: 采购主管
  └── preferred_department: 财务部    ← 用户主动说的
```

- **优点**：准确、无歧义
- **缺点**：用户很少主动说

### 来源 2：隐式行为（CONV_MEM）——丰富但有噪声

从用户历史提问统计分析：统计近 100 轮对话的部门关键词分布，占比 > 50% 才算偏好。

- **优点**：无感、自动
- **缺点**：需要足够样本（至少 20-30 轮）；用户换工作/换项目后画像会过时

### 来源 3：显式工具（模型主动 save）——平衡

新增工具 `saveRetrievalPreference`——用户说"以后问报销问题优先看财务部"时，模型调工具存下。

- **显式场景**（用户明确说了）→ 精确
- **隐式场景**（未说）→ 用来源 2 兜底

**这个方案最适合生产**。

### 存储结构

**新增专用存储**——不混在 USER_PREF 里：

```
RETRIEVAL_PROFILE:user-alice (hash)
  ├── preferred_departments : "财务部,人事部"      ← 逗号分隔
  ├── preferred_doc_types   : "制度,通知"
  ├── weight_bias_vec       : "+0.05"               ← 向量权重偏移
  ├── weight_bias_kw        : "-0.05"               ← 关键词权重偏移
  ├── top_k_bias            : "+1"
  ├── updated_at            : "1790060400000"
  └── source                : "explicit"            ← explicit / implicit
```

**为什么单独一层**：`USER_PREF` 存"用户属性"（城市、语言），`RETRIEVAL_PROFILE` 存"检索偏好"——语义不同。

## 五、与现有四层记忆的整合

**新增第 5 层——检索画像**：

| 层 | 关注点 | 消费者 |
|---|---|---|
| ① CHAT | 当前会话 | MessageChatMemoryAdvisor |
| ② USER_PREF | 用户属性 | PreferenceAdvisor |
| ③ LTM | 重要事实 | MemoryRetrievalAdvisor |
| ④ CONV_MEM | 历史对话 | ConversationRetrievalAdvisor |
| **⑤ RETRIEVAL_PROFILE** | **检索偏好** | **HybridSearchService（间接）** |

**关键整合点**——`ChatService` 构造 `RagFilter` 时叠加画像：

```
① ChatController 从 Session 取硬权限（securityLevel、department）
② ChatService 从 RETRIEVAL_PROFILE 取软偏好
③ 两者合并 → 传入 HybridSearchService
④ 检索时应用"软偏好加分"
```

**新增服务**：`RetrievalProfileService`——负责"读取画像 + 转成权重偏移"。

**改动位置汇总**：

| 位置 | 改动 |
|---|---|
| **新增 `RetrievalProfileService`** | 读画像、算偏移 |
| **`ChatService.streamChatWithMemory`** | 构造 filter 后叠加画像偏移 |
| **`HybridSearchService.weightedFuse`** | 融合分数上叠加"偏好加分" |
| **`ChatClientConfig`** | 新增 `RetrievalProfileService` 依赖 |
| **`application.yml`** | 加 `app.retrieval.profile.enabled: false` 开关 |

## 六、防偏见——四个机制

### 机制 1：倾斜有上限

```java
double MAX_WEIGHT_BIAS = 0.15;    // 融合权重最多偏 15%
double MAX_FILTER_BOOST = 1.20;   // 偏好加分最多 20%
int    MAX_TOPK_BIAS = 2;         // topK 最多偏 2
```

应用时 clamp——防止画像失控。

### 机制 2：画像有 TTL

```
RETRIEVAL_PROFILE:user-alice  TTL = 90 天
```

90 天不更新的画像自动清空——重新用默认参数。**用户换工作、换项目后画像不会永久错乱**。

### 机制 3：画像有"最低样本量"

隐式画像必须样本足够才生效：

```java
if (turnCount < 20) {
    log.info("样本不足（{} 轮），跳过隐式画像", turnCount);
    return RetrievalProfile.empty();
}
```

**为什么**——用户问了 3 个问题，2 个是财务部的——不能就说"偏好财务部"——这是随机波动。

### 机制 4：画像决策有审计日志

每次画像生效都记日志——"为什么这次返回偏了？"——查日志看画像。

## 七、常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| **个性化放宽了安全过滤** | 越权访问 | 硬权限永不个性化——只倾斜软偏好 |
| **倾斜幅度太大** | 用户永远只看到一类文档 | 硬编码上限 15% / 20% |
| **画像永不失效** | 用户换工作后画像错乱 | TTL 90 天 |
| **样本不足就推断** | 误判用户偏好 | 最低 20 轮样本量 |
| **画像写入阻塞主流程** | 每个请求都查询/更新画像 | 画像更新异步化 + 缓存 5 分钟 |
| **隐式画像噪声大** | 统计偏差 | 隐式画像只做"兜底"——显式优先 |
| **个性化后结果太少** | 用户什么都搜不到 | 检测结果数——太少则回退默认参数 |
| **画像和 sessionTag 混淆** | 换会话就丢失画像 | 画像 key 用**纯 userId**——和 tenantId 一致 |

## 九、一句话总结

> **个性化检索不是"记住用户是谁"，而是"从行为推断用户想优先看什么"——从画像到参数的映射。**
>
> **关键设计**：
> - **硬权限 vs 软偏好**严格区分——安全底线永不动摇
> - **倾斜有上限**（15% / 20%）——防止自我强化偏见
> - **画像有 TTL**（90 天）——防止过时
> - **样本有门槛**（20 轮）——防止误判
> - **个性化后结果太少要回退**——防止"什么都搜不到"
>
> **第一版只做"权重倾斜"**——收益明确、风险最低。**过滤偏好和 topK 调整留作后续**。
>
> **和四层记忆的关系**：新增第 5 层 RETRIEVAL_PROFILE——前四层是"记什么"，第五层是"怎么查"——**消费端，不是存储端**。
