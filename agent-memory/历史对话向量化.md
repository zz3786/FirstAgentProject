# 对话历史向量化（Conversation Memory Vectorization）

> D50 核心能力——把每一轮对话向量化后存入 Redis 向量库，
> 支持"跨会话 + 语义"的历史对话召回。

---

## 一、是什么

`ConversationMemoryService` 在每一轮对话结束后，把 **用户原始问题 + AI 最终回答** 打包成一个 `Document`，向量化后存入 Redis 向量库。

检索时，用**用户当前问题**去匹配历史轮次的**向量**——语义相近就召回。

**核心价值**：解决"以前聊过什么类似的"这个问题——这是 CHAT、压缩、LTM、USER_PREF 都覆盖不到的场景。

---

## 二、为什么需要它——三个真实失败场景

### 失败 1：跨会话的"上次那个"

```
会话 A（3 天前）：
  用户："我在做瑞丽市总医院的采购项目"
  AI："好的，我记住了"

会话 B（今天，新 sessionId）：
  用户："上次那个采购项目，进展怎么样了"
  
  CHAT 查什么：CHAT:user-alice:sessionB——新会话，没有上下文 ❌
  LTM 查什么：模型没主动 save 过——无相关记忆 ❌
  USER_PREF 查什么：偏好里没有"项目"信息 ❌
  
  → LLM 只能瞎猜或答"我不清楚" ❌
```

### 失败 2：长会话的早期条款"蒸发"

```
一个 500 轮的长会话：
  第 5 轮："甲方要求质保期 ≥ 3 年"
  第 500 轮："合同里的质保条款是什么"
  
  CHAT 窗口：只保留最近 200 条 → 第 5 轮已滑出 ❌
  压缩摘要："用户讨论了合同主要条款" → 细节丢失 ❌
  
  → LLM 只能模糊回答或说"资料不足" ❌
```

### 失败 3：无法审计"AI 当时为什么这么说"

```
用户投诉："AI 上次告诉我 XX 可以办，现在又不行了"
  
  想查当时 AI 到底说了什么：
  CHAT：会话已过期（TTL 7 天）❌
  压缩：摘要里根本没这条 ❌
  
  → 无法追溯 ❌
```

**对话向量库解决这三个场景。**

---

## 三、与现有四层记忆的关系

| 维度 | CHAT | 压缩 | LTM | USER_PREF | **CONV_MEM** |
|---|---|---|---|---|---|
| 范围 | 当前会话 | 当前会话 | 当前用户 | 当前用户 | **当前用户 + 排除当前会话** |
| 时间跨度 | 最近 200 条 | 摘要 + 最近 200 条 | 长期 | 长期 | **180 天** |
| 精度 | 原文 | 有损摘要 | 精炼事实 | 结构化标签 | **原文** |
| 检索 | 全量注入 | 全量注入 | 中文 2-gram | 按 key 直读 | **向量语义 Top-K** |
| 写入 | 自动 | 自动 | 模型主动 | 模型主动 | **自动** |
| 解决什么 | "刚才聊了什么" | "长会话不爆 Token" | "用户的重要事实" | "用户的偏好" | **"以前聊过什么类似的"** |

**关键差异**：

- **CHAT 是"当前会话的工作记忆"**——只看最近、只在本会话
- **压缩是"长会话的有损摘要"**——按会话、细节丢失
- **CONV_MEM 是"跨会话的精确档案"**——无会话隔离、按语义召回、保留原文

---

## 四、存储结构

### Redis 里的实际形态

```
conv-mem:<UUID> (向量索引条目)
  ├─ text: "我那个退货的事怎么样了"          ← Document.text = user 消息
  └─ metadata:
       user_id           = "user-alice"        ← 用户隔离字段
       conversation_id   = "user-alice:s2"     ← 会话隔离字段
       turn_index        = 5                   ← 轮次序号
       user_message      = "我那个退货的事怎么样了"
       assistant_message = "您订单1001的退货..."
       timestamp         = 1790060400000

conv-turn:user-alice:s2 (string)
  └─ "5"    ← 该会话已进行的轮次数
```

### 数据模型要点

| 字段 | 用途 | 关键设计 |
|---|---|---|
| **text** | 向量化源文本 | **用 user_message**——检索命中率最高 |
| **user_id** | 用户隔离 | 强制过滤——安全底线 |
| **conversation_id** | 会话隔离 | 检索时排除当前会话 |
| **turn_index** | 轮次序号 | 通过 `INCR` 生成——支持按序查看 |
| **user_message** | 用户原话 | 冗余存储——便于调试和展示 |
| **assistant_message** | AI 回复 | **脱敏 + 截断**存储 |
| **timestamp** | 时间戳 | 用于排序 / 时效性判断 |

## 五、写入链路

### 触发时机

**仅在流式响应正常结束时保存**——通过 `doOnComplete` 触发。

```
用户请求 → ChatClient.stream()
    ↓
流式响应正常完成
    ↓
doOnComplete 回调
    ├── 缓存最终答案（semantic-cache）
    ├── ★ 保存对话轮次（conv-mem）
    └── （其他后处理）
```

**不保存的情况**：

| 场景 | 会保存吗 |
|---|---|
| 正常回复完毕 | ✅ |
| 用户主动中断（关闭页面） | ❌ |
| LLM 报错 | ❌ |
| 澄清反问（D47） | ❌——反问是 `Flux.just()`，不经过 doOnComplete |

**为什么这样设计**：半截对话、错误对话、反问，都不值得当"历史对话"存下来。

### 保存逻辑

```java
public void saveTurn(String userId, String conversationId,
                     long turnIndex, String userMsg, String assistantMsg) {
    // ① 前置校验
    if (!props.isEnabled()) return;
    if (userMsg == null || userMsg.isBlank()
            || userMsg.length() < props.getMinUserMessageChars()) return;
    if (assistantMsg == null || assistantMsg.isBlank()) return;

    // ② 脱敏——与 LTM / USER_PREF 保持一致
    String safeUser = SensitiveDataMasker.mask(userMsg);
    String safeAssistant = SensitiveDataMasker.mask(
            truncate(assistantMsg, props.getMaxAssistantChars()));

    // ③ 打包成 Document
    Document doc = new Document(
            safeUser,   // ★ Document.text = user 消息 → 检索命中率最高
            Map.of(
                    "user_id", userId,
                    "conversation_id", conversationId,
                    "turn_index", turnIndex,
                    "user_message", safeUser,
                    "assistant_message", safeAssistant,
                    "timestamp", System.currentTimeMillis()
            )
    );

    // ④ 存向量库
    conversationVectorStore.add(List.of(doc));
}
```

**关键设计点**：

| 设计 | 原因 |
|---|---|
| **Document.text = user_message** | 检索时用"用户问题"匹配"用户问题"——语义分布一致 |
| **assistant_message 单独存 metadata** | 用户问题用于检索，AI 回答用于展示——两者用途不同 |
| **脱敏** | 电话、身份证、银行卡号——存储前统一处理 |
| **截断** | AI 回复可能几万字——截断避免存储爆炸 |
| **不抛异常** | 写入失败不影响主流程——用户问问题成功才是硬道理 |

## 六、检索链路

### 检索时机

在 `ConversationRetrievalAdvisor` 里——用**当前用户问题**去匹配历史轮次：

```java
SearchRequest request = SearchRequest.builder()
        .query(currentUserQuery)                       // 用当前问题去匹配
        .topK(props.getTopK())                          // 只取 Top-K
        .similarityThreshold(props.getSimilarityThreshold())  // 相似度阈值
        .filterExpression(filterExpr)                   // 用户 + 会话过滤
        .build();
```

### 三重隔离

```java
String filterExpr = "user_id == '" + userId + "'";
if (props.isExcludeCurrentConversation()
        && excludeConvId != null && !excludeConvId.isBlank()) {
    filterExpr += " && conversation_id != '" + excludeConvId + "'";
}
```

| 隔离层级 | 条件 | 目的 |
|---|---|---|
| **① 用户隔离** | `user_id == '{userId}'` | 安全底线——绝不跨用户检索 |
| **② 会话隔离** | `conversation_id != '{当前会话}'` | 避免重复——当前会话已由 CHAT 覆盖 |
| **③ 语义隔离** | `similarityThreshold` | 避免噪声——低分结果不返回 |

### 为什么必须排除当前会话

**因为当前会话的内容已经在 CHAT 层注入了**——`MessageChatMemoryAdvisor` 已经把最近消息塞进 Prompt。

**如果不排除**：

```
用户当前问："再详细说说"
   ↓
① CHAT：注入最近 10 条消息（含刚才问的"报销标准"）
   ↓
④ CONV_MEM：语义匹配到"报销标准"这一轮 → 又注入一遍
   ↓
Prompt 里 "报销标准" 出现两次 → Token 浪费 + 模型困惑
```

**排除当前会话后**，④ 只补充"**跨会话的语义相关历史**"——和 ① 天然互补。

## 七、完整数据流

```
用户请求："我那个退货的事怎么样了"
    ↓
┌───────────────────────────────────────────────┐
│ Advisor 链（读）                              │
│ ① MessageChatMemoryAdvisor → CHAT:user-alice:s2 │
│ ② PreferenceAdvisor        → USER_PREF          │
│ ③ RagAdvisor               → 知识库             │
│ ④ MemoryRetrievalAdvisor   → LTM                │
│ ⑤ ConversationRetrievalAdvisor → conv-mem       │
└───────────────────────────────────────────────┘
    ↓
Prompt 组装 → LLM 生成 → 流式返回
    ↓
doOnComplete 触发
    ↓
┌───────────────────────────────────────────────┐
│ 写回（写）                                    │
│ ① semantic-cache ← 存问答对                    │
│ ② CHAT           ← 追加本轮消息                │
│ ③ conv-mem       ← 存本轮向量  ★               │
│ ④ conv-turn      ← INCR 轮次计数               │
└───────────────────────────────────────────────┘
```

**注意**：**CONV_MEM 的写入不在 Advisor 链内**——它在 ChatService 的 `doOnComplete` 里手动调用。因为 Advisor 只能"增强 Prompt"，不能"写业务存储"。

## 八、关键设计决策

### 决策 1：Document.text 用 user_message，不用拼接文本

**方案 A（不用）**：

```java
Document.text = user_message + "\n" + assistant_message;
```

**方案 B（采用）**：

```java
Document.text = user_message;   // 只用用户问题
```

**为什么**：
- 检索时用的是"用户当前问题"——**语义分布一致**才匹配得上
- 如果用拼接文本——检索文本是问题，存储文本是"问题+答案"——**语义分布错位**
- assistant_message 放 metadata——**命中后再取**，不影响检索

### 决策 2：放在 ChatService 手动写，不放 Advisor

**Advisor 的职责**：读取记忆、增强 Prompt。

**Advisor 不能做的事**：写业务存储。

**为什么**：
- Advisor 的 `adviseCall` / `adviseStream` 是"横切关注点"——只管请求/响应的增强
- 写 conv-mem 是"业务副作用"——需要拿到完整的 assistant 回复（流式结束后）
- Advisor 的响应处理是**流式分片**——拿不到完整文本
- 只有 `doOnComplete` 才能拿到完整回复

### 决策 3：写入失败不影响主流程

```java
try {
    conversationVectorStore.add(List.of(doc));
} catch (Exception e) {
    log.warn("对话记忆入库失败（不影响主流程）", e);
    // ★ 不向上抛
}
```

**为什么**：
- 对话记忆是"增强能力"——不是"核心功能"
- 用户**能成功问问题并拿到答案**才是硬道理
- Redis 挂了、向量服务挂了——不该让用户看到"服务出错"

### 决策 4：脱敏 + 截断双重保护

```java
String safeUser = SensitiveDataMasker.mask(userMsg);
String safeAssistant = SensitiveDataMasker.mask(
        truncate(assistantMsg, props.getMaxAssistantChars()));
```

- **脱敏**：电话、身份证、银行卡——存储前统一处理，与 LTM / USER_PREF 一致
- **截断**：AI 回复可能几万字——截断避免存储爆炸
- **顺序**：先截断再脱敏——避免脱敏后长度变化破坏截断逻辑

## 九、配置项

```yaml
app:
  conversation:
    memory:
      enabled: true                    # 总开关
      top-k: 3                         # 检索返回条数
      similarity-threshold: 0.5        # 相似度阈值
      exclude-current-conversation: true  # 是否排除当前会话
      min-user-message-chars: 5        # 用户消息最小长度——太短不存（避免"嗯"、"哦"）
      max-assistant-chars: 2000        # AI 回复最大长度——超出截断
```

| 配置 | 建议值 | 说明 |
|---|---|---|
| **top-k** | 3-5 | 太多会污染 Prompt |
| **similarity-threshold** | 0.5-0.7 | 中文场景 0.5 起步 |
| **exclude-current-conversation** | true | 一般开启——避免重复 |
| **min-user-message-chars** | 5-10 | 过滤"嗯"、"哦"这类无意义消息 |
| **max-assistant-chars** | 2000-4000 | 平衡精度与存储成本 |

## 十、常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **Document.text 用了拼接文本** | 检索命中率低 | 只用 user_message |
| **Advisor 里试图写 conv-mem** | 拿不到完整回复 | 移到 `doOnComplete` |
| **没排除当前会话** | Prompt 里内容重复 | `exclude-current-conversation: true` |
| **没脱敏** | 敏感信息泄漏 | 存前统一 `SensitiveDataMasker.mask()` |
| **没截断** | 存储爆炸 | 限制 `max-assistant-chars` |
| **写入失败向上抛** | 用户看到"服务出错" | try-catch 兜底——不阻断主流程 |
| **短消息也存** | 存储大量"嗯"、"哦" | `min-user-message-chars` 过滤 |
| **Redis metadataFields 没声明** | 过滤静默返回空 | 声明 `user_id` / `conversation_id` 为 TAG |
| **conv-mem 数量远少于问答数** | 保存没触发 | 检查 `doOnComplete` 是否接通、`enabled` 是否为 true |

## 十一、与 CHAT 的配合——四层记忆的"空间-时间"覆盖

```
          时间轴 ────────────────────────────→

        会话 A（3 天前）           会话 B（今天）
        ┌─────────────┐          ┌─────────────┐
CHAT:   │             │          │             │
        │  A 的历史   │          │  B 的历史   │  ← 当前会话
        │  (7天TTL)   │          │  (7天TTL)   │
        └─────────────┘          └─────────────┘
        
CONV_MEM（180 天）:
        ┌─────────────────────────────────────┐
        │  A 的所有轮次    B 的所有轮次        │  ← 跨会话
        │  （向量索引，语义检索）              │
        └─────────────────────────────────────┘
        
LTM（180 天）:
        ┌─────────────────────────────────────┐
        │  重要事实（模型主动 save）           │  ← 跨会话
        └─────────────────────────────────────┘
        
USER_PREF（360 天）:
        ┌─────────────────────────────────────┐
        │  稳定偏好（模型主动 save）           │  ← 跨会话
        └─────────────────────────────────────┘
```

**CHAT 覆盖"当前会话"**——精确、完整、有界。
**CONV_MEM 覆盖"跨会话的历史"**——精确、完整、按语义召回。
**LTM 覆盖"重要事实"**——精炼、跨会话。
**USER_PREF 覆盖"稳定偏好"**——结构化、跨会话。

**四层合起来 = 时间上从"刚刚"到"一年前"、空间上从"当前会话"到"所有会话"的完整覆盖。**

## 十二、生产环境建议

### TTL 设置

| 存储 | 建议 TTL | 原因 |
|---|---|---|
| CHAT | 7 天 | 会话过期后可丢 |
| **CONV_MEM** | **180 天** | 医疗/政务场景需要较长追溯期 |
| LTM | 90~365 天 | 长期事实，但不能永久堆积 |
| USER_PREF | 365 天+ | 偏好变化慢，可长存 |

### 容量估算

**每条 conv-mem 记录的存储开销**：

| 部分 | 大小 |
|---|---|
| 向量（1024 维 float） | 4KB |
| user_message | ~50 字 |
| assistant_message | ~500 字 |
| metadata 其余字段 | ~100 字节 |
| **总计** | **~5KB / 条** |

**每天 1000 轮对话 → 每天 5MB → 180 天 900MB**——可控。

**如果每天 10 万轮**——需要评估存储成本，或缩短 TTL。

## 十三、一句话总结

> **对话历史向量化 = "跨会话 + 语义 + 精确"的历史档案。**
>
> **核心设计**：
> - `Document.text = user_message`——检索命中率最高
> - 三重隔离（用户 + 会话 + 语义）——安全 + 去重 + 降噪
> - 写入在 `doOnComplete`——不在 Advisor（拿不到完整回复）
> - 失败不影响主流程——增强能力，不是核心功能
> - 脱敏 + 截断——保护隐私 + 控制存储
>
> **和 CHAT 的关系**：CHAT 是"当前会话的工作记忆"，CONV_MEM 是"跨会话的历史档案"——**互补，不替代**。
>
> **没有它**：跨会话问"上次那个"、长会话问"早期条款"、审计历史对话——三个场景直接崩。
