## D43 · 混合检索调优

### 课程目标
调整 BM25（关键词）与向量检索的权重配比，让两路召回互补而非相互干扰。

### 核心要点

**1. 两种融合策略**
- **加权融合（Weighted）**：分数归一化后按 `w_vec × norm_vec + w_kw × norm_kw` 求和
- **RRF 融合（Reciprocal Rank Fusion）**：`Σ 1/(k + rank)`，只看排名不看分数

**2. 为什么需要归一化**
- 向量路返回 `distance`（0-1，越小越好）
- 关键词路返回 `score`（0-20+，越大越好）
- 两者量纲不同、方向相反——直接相加无意义
- **必须 Min-Max 归一化 + 方向统一**

**3. 为什么选择 Weighted 而非 RRF**
- Weighted 可精细控制两路权重（如向量 0.7、关键词 0.3）
- RRF 天生等权，无法按业务调整
- **当两路质量明显不同时——必须能按权重倾斜**

**4. 评估集设计原则**
- query 用自然语言，不用文档原文
- 关键词用"文档里特有"的词，不用高频通用词
- 一条 query 配 2-3 个关键词（任一命中即算 hit）
- 评估集必须有区分度——不能全是送分题

**5. 中文关键词检索的关键坑**
- **中文没有空格**——`split(" ")` 会把整句当一个词
- 必须用 **2-gram 滑动窗口**切分（与 MySQL `ngram_token_size=2` 对齐）
- **不要用 `+` 前缀**（必须包含）——过于严格导致零召回
- 用 OR 语义 + `MATCH AGAINST` 的 score 自然排序

### 设计流程回顾

```
查询 → 向量路（Qdrant）+ 关键词路（MySQL 全文索引）
     ↓
   归一化（方向统一为"越大越好"）
     ↓
   加权融合 / RRF
     ↓
   TEI 重排（精筛）
     ↓
   Top-K 返回
```

**为什么这样分层**：粗召回交给两路检索，精筛交给 TEI——每层只做一件事，避免"一路包办所有职责"。

## D44 · 表格抽取

### 课程目标
处理 Excel / CSV，转成"保留列语义"的结构化文本。

### 核心要点

**1. Tika 的致命缺陷**
- Tika 解析 Excel 会把表格**压平成流水文本**
- 列与列的对齐关系彻底丢失
- Embedding 后"张三属于研发部"这条语义召不回来

**2. 三种表格描述策略**

| 策略 | 适用 | 原因 |
|---|---|---|
| **Markdown 表格** | 小表（≤30 行） | LLM 理解最好，支持跨列推理 |
| **KV 逐行描述** | 大表分块 | embedding 抓"字段名=值"共现强 |
| **统计摘要** | 数值列 | 支持聚合类问题 |

**3. 关键设计：表头必须随块走**
- 大表按行分块时，**每块必须重复表头**
- 否则后续 chunk 变"无字段名的值列表"——语义全丢
- **这是新手最容易漏的点**

**4. 解析层的技术细节**
- 用 `DataFormatter` 而非 `getStringCellValue()`——后者遇到数值列会崩
- 空表头补占位名（"列1"、"列2"）——避免"=值"的无字段 KV
- 列数补齐——防止某些行短于表头导致 KV 错位

### 设计流程回顾

```
文档解析入口（按后缀分派）
     ├── Excel/CSV → TableExtractService（已按行分块）
     ├── PDF      → PagePdfDocumentReader
     └── 其他     → Tika 万能解析
     ↓
统一 metadata 注入
     ↓
向量化 + MySQL
```

**为什么这样分派**：把"表格 vs 文本"的差异收敛到 `DocumentParseService` 内部，主干 `ingestWithTika` 保持 6 段 StopWatch 对称——**主干不分支**。

## D45 · 图片 OCR

### 课程目标
对文档中的图片进行文字提取（Tesseract）。

### 核心要点

**1. 三类输入都要考虑**
- 独立图片文件（jpg/png/...）
- 扫描件 PDF 的页面（**无文本层，纯图片**）
- 文档内嵌图片（进阶，本课未做）

**2. Tesseract 的非线程安全**
- native 句柄不是线程安全
- **必须每个线程独立实例**——用 `ThreadLocal` 是最轻量的方案
- 共享实例会导致 native crash（不可被 try-catch）

**3. 超时控制是硬需求**
- 坏图 / 超大图会让 Tesseract 卡死
- 用 `Future.get(timeout)` 强制中断
- 不设超时 → 一批文件全部阻塞

**4. OCR 结果必须清洗**
- Tesseract 对低质量图产生大量噪声字符
- 直接入向量库会污染检索
- 清洗策略：去连续空行、合并连续空格、去掉噪声符号
- **minTextLength 过滤**——少于 N 字视为无有效文本

**5. 扫描件 PDF 的逐页判断**
- 先用 PDFBox 提取文本层
- 空文本的页 → 渲染为图片 → OCR
- **不能整份判断**——混合型 PDF（前几页文本、后几页扫描）很常见
- 300 DPI 是精度与速度的平衡点

**6. 语言包依赖链**
- `chi_sim+eng` 配置 → 加载 chi_sim、eng
- Tesseract 5.x 会**关联加载 `chi_sim_vert`**（竖排增强）
- 缺失会报错但 OCR 仍能跑——补上让日志干净

### 设计流程回顾

```
文档解析入口
     ├── 图片文件   → ImageDocumentReader → OcrService
     ├── PDF       → parsePdf（含逐页 OCR 补丁）
     └── 其他      → Tika
     ↓
OcrService.ocr(image, sourceId)
     ├── ThreadLocal 拿独立 Tesseract 实例
     ├── Future 提交任务
     ├── get(timeout) 强制超时
     └── 清洗 + 长度过滤
```

**为什么 OcrService 只做"图→文"**：职责单一——图片文件、PDF 页都能复用它，不感知上下文。

## D46 · 元数据过滤

### 课程目标
用 VectorStore 的过滤表达式，按时间、部门等标签精准过滤。

### 核心要点

**1. 过滤必须在检索时而非检索后**
- 检索后过滤：先召回 Top-K 再丢弃——浪费计算
- 检索时过滤：Qdrant 在 HNSW 遍历时跳过——几乎零成本
- **前提：必须建 Payload Index**

**2. Redis 和 Qdrant 的行为差异（最大的坑）**

| | RedisVectorStore | QdrantVectorStore |
|---|---|---|
| 过滤能力 | **必须显式声明 metadataFields** | 开箱即用 |
| 未声明时 | **静默返回空** | 正常过滤 |
| 字段类型 | 必须指定 TAG/TEXT/NUMERIC | 动态推断 |

**3. 过滤字段的分类**
- **筛选维度**（前端可传）：department / year / docTypes
- **权限维度**（服务端强制）：securityLevelMax
- **默认策略**（服务端设默认）：status
- **判断标准**："这个参数是筛选范围还是决定权限？"——后者永不交给前端

**4. RagFilter 用 record 而非 Map**
- Map 丢失类型信息、调用方不知合法 key
- record 显式声明"合法过滤维度"——契约清晰、IDE 可补全
- **保留旧构造签名**——避免破坏已有调用点

**5. 过滤结果的传递机制**
- Advisor 方法签名固定，无法加参数
- 用 `ChatClientRequest.context()` 传参——和 `CONVERSATION_ID` 同一机制
- `param()` 拒绝 null——null 时不传这个 key

**6. 过滤无结果时绝不降级**
- 过滤"财务部"返回空 → 就返回空
- 降级为"不过滤"会破坏语义——用户看到不该看的内容
- 让模型说"根据现有资料无法回答"

**7. Payload Index 的建法**
- 启动时用 `ApplicationRunner` 建——保证 QdrantClient 已就绪
- 用 `@Order(50)` 让它在 `RagStartupRunner(100)` 之前执行
- 幂等——已存在时抛异常，捕获后忽略

### 设计流程回顾

```
写入侧：
  文件入库 → injectMetadata 补过滤字段
       ├── department（从目录名推断）
       ├── year（文件名 → 修改时间 → 当前年）
       ├── content_type（解析器填 / 兜底 "text"）
       ├── security_level（默认 1）
       └── status（默认 "active"）
           ↓
  Qdrant payload + MySQL 列

检索侧：
  RagFilter → toExpression() → Qdrant filterExpression
           → cacheKeySuffix() → 语义缓存 key

缓存侧：
  cacheKey = {tenantId}::{departments}|{yearRange}|{types}|{sources}|{secLevel}|{statuses}
```

**为什么 filter 要纳入 cache key**：
- 缓存 key 语义是"什么输入产生什么输出"
- 同一 query 在"财务部"和"研发部"过滤下答案不同
- 不加 filter → 命中错误缓存 → 比不用缓存更糟

## D47 · Agent 主动追问

### 课程目标
检索结果不明确时，Agent 反问用户澄清。

### 核心要点

**1. 三个"模糊"信号**
- 最高分低（`max(rerank_score) < minTopScore`）
- 高分项太少（`count(score >= 阈值) < minQualifiedDocs`）
- 来源太散（进阶，本课未做）

**2. 决策点必须能"短路"**
- **Advisor 不能短路**——必须走完 `nextCall`
- **工具不能短路**——它是"被调用者"，没有控制流权限
- **只有 ChatService（调用层）能短路**

**3. 三层控制流的能力对照**

| 位置 | 能修改请求 | 能短路 | 决策者 |
|---|---|---|---|
| **ChatService** | ✅ | ✅ | 代码（你） |
| **Advisor** | ✅ | ❌ | 代码（你） |
| **工具** | ❌ | ❌ | LLM |

**4. 前置检索——一次检索，两用**
- 提到 ChatService 层做一次
- 用于①澄清判定 ②传给 RagAdvisor 注入
- **避免重复 embedding / Qdrant 往返 / TEI 重排**
- 通过 `advisor param("prefetched_docs", docs)` 传递

**5. 反问文本的识别机制**
- 前缀 `[CLARIFY]` 让前端识别
- 前端剥离前缀 → 特殊渲染（黄色气泡）
- **反问不存缓存**——否则第二次问还是反问

**6. 工具为什么不参与澄清判定**
- LLM 决定"要不要检查"——但"要不要检查"是系统策略
- 工具返回后 LLM 还会生成一次——反问文本会被加工
- LLM 可能忽略工具结果——"我觉得我能答"
- **判断标准：业务语义选择 vs 系统级策略——后者必须代码强制**

### 设计流程回顾

```
用户请求
   ↓
① 语义缓存查询（命中直接返回）
   ↓
② 前置 RAG 检索（一次检索，两用）
   ↓
③ 澄清判定
   ├── 模糊 → 返回 [CLARIFY] 反问文本，不调 LLM
   └── 明确 → 继续
   ↓
④ 调 LLM（Advisor 链）
   ├── MessageChatMemoryAdvisor
   ├── CompactingChatMemoryAdvisor
   ├── PreferenceAdvisor
   ├── RagAdvisor（用 prefetched_docs，不重复检索）
   ├── MemoryRetrievalAdvisor
   └── ToolLoggingAdvisor
   ↓
⑤ 缓存最终答案（反问走不到这里）
```

**为什么决策点必须在 ChatService**：因为"要不要调 LLM"这个决策**只有调用层能做**——Advisor 和工具都在 LLM 调用链内部或之后。

## D48 · 整合主项目

### 课程目标
将 RAG 模块合并到第一阶段项目中。

### 核心要点

**1. 模块依赖关系**

```
agent-tools  →  agent-memory  →  agent-core  →  agent-api
                    ↑                ↑
              agent-cache  →  agent-rag
```

**2. 分层原则**
- **agent-tools**：给 LLM 调用的工具（@Tool 注解）
- **agent-rag / agent-memory / agent-cache**：领域服务
- **agent-core**：装配层 + 编排层
- **agent-api**：Controller + 全局异常

**3. 避免循环依赖**
- agent-cache 不能依赖 RagFilter（在 agent-rag）——改用 String 传参
- agent-rag 依赖 agent-cache——方向单一

**4. 主干不分支的设计**
- `ingestWithTika` 保持 6 段 StopWatch 对称
- 分派逻辑下沉到 `DocumentParseService`
- `injectMetadata` 用 `putIfAbsent` 幂等

**5. 配置外置原则**
- OCR 路径、语言、超时 → `OcrProperties`
- 检索 topK、权重、阈值 → `RagProperties`
- 澄清阈值 → `ClarificationProperties`
- **改参数不改代码**

## 跨课程的核心设计哲学

### 1. 主干不分支
所有"文件类型分派"逻辑集中在 `DocumentParseService.parse()`——
`ingestWithTika` 只看 `alreadyChunked` 标志，不知道该文件是表格还是图片。

### 2. 分层——每层只做一件事

```
检索层（粗召回） → 融合层（加权） → 重排层（精筛） → 注入层（Prompt）
```

不让任何一层"包办所有职责"。

### 3. 职责边界清晰
- `DocumentParseService`：文件 → Document
- `TableExtractService`：Excel/CSV → 保留列语义的 Document
- `OcrService`：图片 → 文本
- `injectMetadata`：补通用元数据
- **每层不越界**

### 4. 契约显式化
- `RagFilter` 用 record 而非 Map
- `ParseResult` 用 record 携带 `alreadyChunked`
- `DocInfo` 用 record 携带 `sourcePath` / `lastModified`

### 5. 过滤决定权分层
- 筛选维度 → 前端可传
- 权限维度 → 服务端强制
- 默认策略 → 服务端设默认

### 6. 缓存 key 语义完整
- `{tenantId}::{filter_suffix}`——包含所有影响输出的因素
- 集合维度排序——顺序无关
- 无过滤时 suffix 为空——结构一致

### 7. 短路权限只属于调用层
- Advisor：能增强，不能短路
- 工具：能拦截执行，不能短路
- **ChatService：唯一能"在 LLM 之前做决策"的位置**

### 8. 数据的完整性 > 功能的完整性
- department/year 一定有值（兜底"通用"/当前年）
- 无值会导致过滤永远返回空
- **宁可兜底，不可留 null**

## 常见坑速查

| 课 | 坑 | 现象 | 解法 |
|---|---|---|---|
| D43 | 中文 split 无空格 | 关键词路零召回 | 2-gram 切分 |
| D43 | `+` 前缀过严 | 整句必须出现 | 用 OR 语义 |
| D43 | 权重调优无区分度 | HitRate 恒定 | 评估集要有区分度 |
| D44 | Tika 压平表格 | 列语义丢失 | 专用解析器 |
| D44 | 表头不随块走 | 大表 chunk 无语义 | 每块重复表头 |
| D45 | Tesseract 共享实例 | native crash | ThreadLocal |
| D45 | 无超时控制 | 坏图阻塞入库 | Future.get(timeout) |
| D45 | OCR 噪声污染 | 检索召回了竖线符号 | 清洗 + 长度过滤 |
| D46 | Redis 未声明 metadataFields | 过滤静默返回空 | 显式声明 TAG |
| D46 | Qdrant 无 Payload Index | 大数据量断崖变慢 | 启动时建索引 |
| D46 | filter 未纳入 cache key | 命中错误缓存 | 复合 key |
| D47 | Advisor 试图短路 | 无法返回反问 | 前置判定在 ChatService |
| D47 | 反问存了缓存 | 二次提问还反问 | 反问不存缓存 |
| D47 | prefetched_docs 类型判断 | try/catch 里赋值两次 | 抽方法保证有效 final |

## 一句话总结每课

- **D43**：混合检索的价值不在"用了两路"，而在"让两路互补"——归一化方向统一，中文 2-gram 切分，权重可调。
- **D44**：表格抽取的价值不在"能读 Excel"，而在"保留列语义"——表头随块走、KV 描述、按行切。
- **D45**：OCR 的价值不在"能识别文字"，而在"稳定可控"——ThreadLocal 保线程安全、Future 保超时、清洗保质量。
- **D46**：元数据过滤的价值不在"筛掉不相关的"，而在"让过滤成为检索的默认动作"——Payload Index 加速、cache key 隔离、权限维度不可绕。
- **D47**：主动追问的价值不在"能反问"，而在"知道什么时候该反问"——决策点放在调用层、前置检索一次两用、反问不入缓存。
- **D48**：整合的价值不在"合并代码"，而在"依赖方向单一 + 主干不分支 + 配置外置"。
